# 写作规范

## 0. 项目愿景

**本项目的终极目标**：让一个零基础的小白，完全在这一个网站上就能学会 RL、深度学习、以及机器人学习的所有相关知识。读者不需要翻论文原文、不需要找其他教程——这里就是他的唯一学习入口。

为了实现这个愿景，必须遵守以下核心原则：

### 知识自包含原则

- **遇到任何超出大学本科水平的概念，必须自动写一篇前置知识去解释它**。不能假设读者知道 KL 散度、ELBO、GAE、Actor-Critic 是什么——每一个都要有独立的前置知识文章。
- **判断标准**：如果一个概念对"有基本线代和概率知识的本科生"来说需要学习，就必须有前置知识文章。
- **执行方式**：写任何文章时，遇到需要解释的概念，如果已有前置知识就链接过去；如果没有，**立刻创建**对应的前置知识文件（哪怕先写个框架后面再填充），绝不留空白。

### 前置知识的原子性与无重复原则

- **原子化**：一篇前置知识只讲**一个**概念。"SAC"是一篇、"DDPG"是一篇、"Q 函数"是一篇、"Replay Buffer"是一篇。绝不在一篇里塞两个独立概念。
- **无重复**：同一个概念在整个项目中只有**一个**权威讲解位置。如果"Q 函数"在 SAC 文章中需要解释，不要在 SAC 文章里重新讲一遍 Q 函数——链接到 Q 函数的前置知识文章就行。
- **粒度判断**：如果一个子概念在多篇文章中被反复解释，说明它应该被提取为独立的前置知识。反之，如果一个概念只在一篇文章中出现一次且 3 句话能说清，可以内联解释不用单独成文。

### 知识图谱式的链接网络

项目的所有文章构成一个**有向无环图（DAG）**：
- 前置知识 → 前置知识（如"DDPM" → "对数似然与 ELBO"）
- 前置知识 → 论文精读（如"PPO" → "DPPO 精读"）
- 论文精读 → 综述（如"DPPO 精读" → "扩散策略 RL 综述"）

读者可以从任何一个节点进入，顺着链接探索整个知识体系，永远不会遇到"这个概念没解释"的断点。

### ⚠️ 知识全阶段覆盖原则（极其重要）

**任何一个知识点，必须覆盖从原理 → 概念 → 具体应用的完整链路，一个阶段都不能少。**

具体来说，当介绍一个新概念/方法时，必须包含以下四个阶段（可以在同一篇文章中，也可以拆分成多篇互相链接）：

1. **基础原理阶段**：这个概念依赖的底层数学/物理直觉是什么？
   - 例：介绍 LoRA 时，不能跳过"矩阵的秩"这个概念。必须有一篇独立的前置知识解释秩是什么、为什么低秩矩阵可以压缩。
   
2. **概念/算法阶段**：这个方法本身的设计是什么？公式是什么？为什么这样设计？
   - 例：LoRA 的 $\Delta W = BA$，$\alpha/r$ 缩放，初始化策略等。

3. **工程实操阶段**：具体怎么用？模型怎么改？代码怎么写？训练流程是什么？
   - 例：LoRA 怎么注入模型、训练时梯度怎么流、部署时怎么合并。必须有可运行的代码示例。
   - **这一阶段绝不能省略！** 很多读者在"公式我看懂了但不知道怎么实际操作"这一步卡住。

4. **应用场景阶段**：在真实项目中怎么用？有什么最佳实践？踩过什么坑？
   - 例：LoRA 在 VLA 中怎么配置、$r$ 怎么选、哪些层加哪些层不加、和 RL 怎么配合。

**执行方式**：
- 写任何概念时，自查这四个阶段是否都有对应的文章覆盖
- 如果某个阶段缺失，立即创建对应文章（哪怕先写个骨架）
- 在文章中用链接把四个阶段串联起来，让读者能顺畅地从原理一路读到应用

**反面例子（禁止）**：
- 只讲公式不讲怎么用 → 读者知道 $\Delta W = BA$ 但不知道代码怎么写
- 只讲代码不讲原理 → 读者会用但不知道为什么这样用
- 只讲概念不讲应用场景 → 读者不知道在自己的项目中该怎么配置

**正面例子（要求）**：
LoRA 知识体系应该有这样的完整链路：
- [矩阵的秩与低秩近似](/前置知识/000z_前置知识_矩阵的秩与低秩近似)（原理阶段）
- → [LoRA 低秩适配基础](/前置知识/000x_前置知识_LoRA低秩适配基础)（概念阶段）
- → [LoRA 实操全流程](/前置知识/001a_前置知识_LoRA实操全流程_模型如何支持LoRA)（工程实操阶段）
- → [LoRA 在 VLA 中的应用](/论文综述/067_LoRA_VLA_机器人视觉语言动作模型适配)（应用场景阶段）

读者沿着这条链路读下来，从"秩是什么"一直读到"在我的机器人项目里 r 应该设多少"，没有任何断点。

## 1. 面向读者：小白友好 + 有深度

### 核心原则

- **假设读者是聪明的本科生**：有基本数学素养（线代、概率），但不了解具体领域。任何超出这个基线的知识（如 KL 散度、策略梯度、扩散模型、变分推断），都必须有前置知识文章兜底
- **每个公式必须"拆碎了讲"**：不能只列公式，必须逐项解释每个符号的含义、为什么是这个形式。**公式出现之前必须先用自然语言交代"这个公式是用来干什么的"**——读者必须在看到公式之前就知道它要解决什么问题。绝不允许毫无铺垫地甩出一个公式。
- **先直觉再形式**：任何概念先用一句话说明"在干什么"，再给严格定义
- **举例子！举例子！举例子！**：最好有一个**贯穿全文的具体例子**（如"一个 2D 桌面上的机器人抓取"），每次引入新概念时都用这个例子来解释
- **⚠️ 必须比原论文更详细**：不论是精读还是综述，写出来的内容必须比原论文更加详细、更加易懂。原文一笔带过的地方，我们要展开讲清楚；原文没有例子的地方，我们要补充具体数值例子；原文跳步的推导，我们要补全中间步骤。**绝不允许一句话概括一个方法就跳过**——如果一个概念值得提，就值得花几段话把它讲透。这是本项目存在的意义：让读者读我们的文章就够了，不需要再回去看原文。
- **⚠️ 新概念/组件引入必须先建立连接**：任何新出现的概念、模块或组件，必须在引入时**立刻回答三个问题**：
  1. **它和已有系统是什么关系？**——比如"这个模块插在 VLA 的 Transformer backbone 之后、action head 之前"，或者"它替换了原来的 xxx 模块"。必须让读者能在脑中把新概念"放进"已有的系统架构图里。
  2. **在什么阶段使用？**——是训练时用？推理时用？两者都用？在整个 pipeline 的第几步？
  3. **为什么需要它？设计初衷是什么？**——解决了什么之前解决不了的问题。
  
  **反面例子**（禁止）：直接说"TOPIC 由三个组件构成：Task-Specific Prompt Pool、Task Relation Graph、Graph-guided Initialization"——读者读到这里完全不知道这些东西和 VLA 模型是什么关系，在哪里插入，什么时候用。
  
  **正面例子**（要求）：先说"标准 VLA 在顺序学习新任务时，新任务的梯度会覆盖旧任务的参数→遗忘。一种解法是：冻结 VLA 的整个 backbone，改为在输入序列前面插入一小组可学习向量（称为 prompt），每个任务只训练各自的 prompt（约 80K 参数）。这样不同任务的参数完全隔离，就不存在覆盖问题。"——读者立刻明白了 prompt 在系统中的位置（输入端）、阶段（训练时学习，推理时选择）、和 VLA 的关系（backbone 冻结，prompt 是唯一可变部分）。
- **⚠️ 遇到未覆盖的概念必须主动补充**：写文章过程中，一旦发现引用了一个还没有对应前置知识的概念（如提到 DDPG 但没有 DDPG 前置文章），必须**立即创建**那篇前置知识（至少创建文件+写好骨架），不能只留 TODO 不管。项目的完整性比任何单篇文章的完成度更重要。
- **⚠️ 代码必须"先讲后贴"，禁止直接甩代码**：任何代码块出现之前，必须先用自然语言讲清楚这段代码**要做什么、为什么这样做、核心思路是什么**。读者应该在看到代码之前就已经理解了设计意图，代码只是"验证"他的理解。具体要求：
  1. **代码前必须有文字铺垫**：至少 2-3 句话说明"接下来这段代码要实现什么功能"、"核心思路是 xxx"。
  2. **禁止连续贴多段代码**：两段代码之间必须有文字解说，解释前一段代码的关键点、引出后一段代码的动机。
  3. **代码中的关键行必须有注释或紧跟讲解**：如果一行代码的含义不显而易见（如 `torch.bmm(x, selected_W)`），必须在代码注释中或代码块后面解释它在做什么。
  4. **先概念后实现**：引入一个新模块时的正确顺序是——(a) 这个模块解决什么问题 (b) 它的设计思路是什么 (c) 具体实现（代码）(d) 代码中值得注意的细节。绝不允许 (a) 之后直接跳到 (c)。
  
  **反面例子**（禁止）：
  > "N1.7 的 MultiEmbodimentActionEncoder：" 然后直接贴 20 行代码。
  
  **正面例子**（要求）：
  > "N1.5 的问题是所有机器人共享一组权重——Franka 的'关节角'和 G1 的'左臂角度'虽然语义完全不同，却被迫通过同一个线性层映射。N1.7 的解决方案是：给每种机器人分配一组**独立的**权重矩阵。具体做法是把普通的 `nn.Linear` 替换为 `CategorySpecificLinear`——它内部存储了 N 组权重，前向传播时根据 `embodiment_id` 选择对应的那一组。来看实现："

### ⚠️⚠️⚠️ 公式必要性原则：不为了写公式而写公式（最高优先级，所有 Agent 必须遵守）

**默认不放公式。只有满足下面两个条件之一，才允许放独立公式（$$...$$）：**

1. **不用公式讲不清楚**：这个概念的精确含义依赖符号之间的数学关系，脱离公式用纯文字描述会丢失关键信息或变得啰嗦难懂（比如损失函数里每一项的确切权重关系、变量替换的雅可比修正）。
2. **公式能让理解更清晰**：读者已经通过文字获得了直觉，公式在此基础上给出一个精确、简洁的总结，方便和其他方法对比或方便记忆（比如用一行公式总结"策略梯度 = 优势 × log-prob 梯度"，比大段文字更容易记住形式）。

**如果两个条件都不满足，就不要放公式**——用文字、类比、伪代码描述思路即可。判断标准：删掉这个公式，只留文字讲解，读者是否依然能完全理解这个概念在做什么、为什么这样设计？如果答案是"能"，这个公式就是可以删掉的装饰品，必须删掉。

**常见的"为了写公式而写公式"的违规模式**（必须杜绝）：

1. **把教科书里的标准公式原样搬进来"意思一下"**：比如讲策略梯度定理时，正文已经在讲 PPO 的具体改动，却又完整搬一遍 $\nabla_\theta J = \mathbb{E}[\hat{A}_t \nabla_\theta\log\pi_\theta(a_t|s_t)]$ 这个通用公式——如果这个公式在对应的前置知识文章里已经讲过，这里直接一句话带过并链接过去即可，不需要重新完整详解一遍。
2. **一篇文章里公式密度过高，每小节都是"结论一句话 + 公式 + 折叠详解"的模板化重复**：这样读起来变成"翻译公式"而不是"讲解概念"，读者的注意力被大量结构相似的折叠块耗尽，反而抓不住真正的重点是什么。**一篇精读/综述里，真正需要现场详解的独立公式一般不应超过 5-8 个**——如果某个概念的公式在前置知识里已经讲过，这里只放最终形式（不重复详解）或者干脆只用文字复述结论。
3. **给中间步骤、显然的代入、简单的记号定义也套用公式详解模板**：比如"设 $x=a+b$"这种纯记号定义、或者两个数相加这种不需要解释的代入，不需要公式详解模板，用一句文字带过或者干脆写成行内公式 $x=a+b$ 就够了，不需要单独起一个 `$$...$$` 块再配一个折叠详解。

**反面例子（禁止）**：《FlowRL：Flow VLA 的在线 RL 微调》精读通篇 38 个独立公式，其中标准策略梯度定理、KL 散度定义、Flow Matching 的 CFM loss 等在项目里已有对应前置知识文章覆盖的内容，被重新完整详解了一遍——正确做法是这些内容只需一句话点出"用的是标准 XX（链接过去）"，精读的公式密度应该只保留 FlowRL **本身特有**的贡献（两种 log-likelihood 近似方法的公式），其余全部压缩成文字总结 + 链接。

**判断一篇文章公式密度是否合格的自查方法**：数一下文章里独立公式的数量，再问自己——这些公式里，有多少是"这篇文章的独创贡献"，有多少是"教科书里随处可查的标准定义"？如果后者占比超过一半，说明公式放多了，应该把标准定义压缩成文字+链接，只保留这篇文章独有的、必须用公式才能精确表达的部分。

### ⚠️ 公式讲解模板（最高优先级规则）

**满足上面"公式必要性原则"、确实需要放公式之后，每一个独立公式（$$...$$）后面都必须紧跟详细讲解，没有例外！** 绝不允许写完公式就跳到下一个话题。

**这条规则适用于所有文章类型：前置知识、论文精读、综述。没有例外。**

#### 核心方法：子表达式角色化讲解

**公式讲解的核心不是逐符号查字典，而是把公式中的子表达式赋予"角色"，用大白话讲出各部分在"演什么戏"。**

每个重要公式后必须包含：

1. **这个公式在做什么**（1-2 句话，加粗，不折叠）：读者哪怕不展开详情也知道公式目标。
2. **子表达式角色化拆解**（表格，折叠块内）：把公式拆成 3-5 个"角色"，每个角色是一个**子表达式整体**（如 $\epsilon_\theta(\mathbf{A}_t, t, z)$），说明"它是谁、它在干嘛"。用拟人化语言。
3. **用人话读公式**（1-2 句话，折叠块内）：一句不含数学符号的中文完整复述公式含义。
4. **为什么是这个形式**（1-2 句话，折叠块内）：设计动机。

**以下内容是可选的（不再强制）**：
- 逐符号细节表（某个符号确实不透明时才补充）
- 数值代入（能显著帮助理解时才加，不是每个公式都需要）

### ⚠️⚠️ 公式讲解的执行检查清单（强制执行）

以下**违规模式**必须杜绝：

1. **只逐符号解释，没有子表达式整体含义**：$f_\theta(x,t,z)$ 必须先作为整体赋予角色（如"网络对噪声的猜测"），再讲里面每个字母。
2. **没有"用人话读公式"**：讲解完读者应能用一句不含数学的中文复述公式含义。
3. **多项 loss 只解释整体**：$L = A + B - C$ 每一项都要有独立角色，说清"拉什么往哪走"。
4. **期望 $\mathbb{E}$ 没说"实际训练中怎么近似"**：mini-batch？Monte Carlo？全量？
5. **含梯度 $\nabla$ 没解释方向的物理含义**。
6. **禁止"显然"、"容易验证"、"不难看出"**。

**自查方法**：写完公式讲解后——一个没学过本领域的聪明本科生，只读你的讲解，能不能用一句大白话说出"这个公式在干嘛、各部分是什么角色、为什么这样设计"？能 → 合格。

### ⚠️⚠️⚠️ 所有公式的强制详解规范（最高优先级）

**每一个独立公式（$$...$$）都必须按以下标准详解。没有"这个公式比较简单所以可以略过"的例外。**

#### 规则 A：单个公式的强制格式

**Step 1：可见摘要（不折叠）**
- 1-2 句话加粗，说明公式在做什么
- 用最直觉的语言

**Step 2：角色化详解（折叠块内）**
- 表格：`| 子表达式 | 它是谁 | 它在干嘛 |`
- "用人话读"：一句不含数学符号的中文
- "为什么是这个形式"：设计动机

#### 规则 B：多项公式的额外要求

当 $L = A + B + C$ 时，每一项是独立角色，说清项间的对抗/协作关系。

#### 正面示范

```markdown
$$
\mathcal{L}_{\text{flow}} = \mathbb{E}_{t, \mathbf{A}_0, \mathbf{A}_1} \left[ \| v_\theta(\mathbf{A}_t, t, z) - (\mathbf{A}_0 - \mathbf{A}_1) \|^2 \right]
$$

**这个公式在做什么**：在噪声和动作之间画一条直线，让网络学会"站在路上任何一点，指出正确的前进方向"——指得越准 loss 越低。

::: details 📐 公式详解（点击展开）

| 子表达式 | 它是谁 | 它在干嘛 |
|---------|--------|---------|
| $\mathbf{A}_0 - \mathbf{A}_1$ | **GPS 导航** | 从噪声到真实动作的正确方向 |
| $v_\theta(\mathbf{A}_t, t, z)$ | **旅行者的猜测** | 网络站在路上某点，猜"我该往哪走" |
| $\|v_\theta - (\mathbf{A}_0-\mathbf{A}_1)\|^2$ | **偏差评分** | 猜的方向和正确方向差多少 |
| $\mathbb{E}_{t,\mathbf{A}_0,\mathbf{A}_1}$ | **公平考试** | 随机抽不同路段位置和样本，所有情况取平均 |

**用人话读**："随机在噪声→动作的直线路上停一点，问网络往哪走，和正确方向的偏差就是 loss。"

**为什么路径是直线**：直线 = 最短路径（最优传输），积分时大步走也不偏，所以只需 5-10 步就能从噪声走到动作。
:::
```

```markdown
$$
\mathcal{L}_{\text{flow}} = \mathbb{E}_{t, \mathbf{A}_0, \mathbf{A}_1} \left[ \| v_\theta(\mathbf{A}_t, t, z) - (\mathbf{A}_0 - \mathbf{A}_1) \|^2 \right]
$$

其中 $t$ 是时间，$\mathbf{A}_0$ 是数据，$\mathbf{A}_1$ 是噪声，$v_\theta$ 是速度场网络，$z$ 是条件。
```

### 前置知识引用原则

- **公式中出现的通用概念**（如 $Q(s,a)$、$V(s)$、advantage、GAE、KL 散度、交叉熵等），如果不是本文主题，**必须链接到前置知识文章**
- **前置知识应该原子化**：一篇前置知识只讲一个概念（如"Q 函数与 Value 函数"是一篇、"GAE 优势估计"是一篇），但必须讲透、讲明白
- **判断标准**：如果一个符号/概念需要超过 3 句话才能解释清楚，它就应该有自己的前置知识文章
- **行文中遇到需要前置知识但还没写的文章时**：先写一个占位链接标注 `<!-- TODO: 需要前置知识文章 -->`，然后尽快补充

### ⚠️ 前置知识的独立性原则（极其重要）

**前置知识是上游，论文精读/综述是下游。** 依赖关系只能单向流动：论文可以引用前置知识，但前置知识绝不能依赖某篇论文的上下文。

具体要求：
- **前置知识必须完全独立于任何论文**：讲 SAC 就讲 SAC 本身，不要说"为了训练 Residual 网络所以用 SAC"。这种应用场景的描述属于论文精读的内容。
- **前置知识的例子必须是通用的**：用"一个机械臂学习抓取"或"一个小车学平衡"这种通用场景，不要用某篇论文特有的场景（如"VLA 的 Residual 修正网络"）
- **前置知识的动机必须是概念本身的动机**：讲 SAC 的动机是"连续动作空间需要 sample-efficient 的 off-policy 方法"，而不是"Residual RL 需要用 SAC"
- **论文精读中再做关联**：在论文精读中写"本文使用 [SAC](/前置知识/000k_前置知识_SAC_Soft_Actor_Critic) 训练 Residual 网络，具体原因是……"

**判断标准**：如果删掉项目中所有论文精读和综述文章，前置知识文章读起来仍然完整、自洽、有价值——这就对了。前置知识是**教科书式的基础概念讲解**，不是某篇论文的配套说明。

示例：

```markdown
$$
L^{\text{CLIP}}(\theta) = \mathbb{E}\left[\min\left(r_t(\theta)\hat{A}_t, \; \text{clip}(r_t(\theta), 1-\epsilon, 1+\epsilon)\hat{A}_t\right)\right]
$$

**这个公式在做什么**：让策略朝着"好动作"更新，但用 clip 机制阻止一次更新太大——相当于给策略更新加了安全绳。

::: details 📐 公式详解（点击展开）

| 子表达式 | 它是谁 | 它在干嘛 |
|---------|--------|---------|
| $r_t(\theta)\hat{A}_t$ | **自由更新方向** | 概率比 × 优势。"这个动作好（$\hat{A}>0$），我把它的概率提高了 50%（$r=1.5$），收益 = $1.5 \times A$" |
| $\text{clip}(r_t, 1-\epsilon, 1+\epsilon)\hat{A}_t$ | **限速版本** | 把概率比强行卡在 $[0.8, 1.2]$ 范围内再算收益——"就算你想提 50%，我只允许你提 20%" |
| $\min(\cdot, \cdot)$ | **安全裁判** | 两个版本取较小的。效果：好动作不能涨太猛，差动作不能压太狠 |
| $\mathbb{E}[\cdot]$ | **全局平均** | 对一个 batch 里所有 (state, action) 取期望 |

**用人话读**："对每个动作算'不限速收益'和'限速收益'，取较小的作为目标——确保策略每次只走一小步。"

**为什么 clip 而不是 KL 惩罚**：clip 实现简单、无需调 KL 系数，且经验上效果一样好。
:::
```

## 2. 交叉引用：文章之间必须互相链接

### 规则

- **前置知识引用**：文章中首次出现一个非本文主题的重要概念（如"PPO"、"DDPM"）时，必须用超链接指向对应的前置知识文章
- **前置知识之间也要互相引用**：前置知识不是孤岛！如果 SAC 文章提到了 DDPG / TD3，就必须链接到对应的前置知识。如果对应的前置知识还没写，先留 `<!-- TODO: 需要前置知识文章：DDPG/TD3 -->` 占位，但**绝不能只一句话带过不加链接**。前置知识之间的网状引用关系是帮助读者构建知识体系的关键——读者应该能从任何一篇入口，顺着链接阅读完所有相关前置知识。
- **论文之间引用**：综述引用精读、精读引用综述、综述之间引用，只要内容相关就加链接
- **知识链接区**：每篇文章开头必须有"相关阅读"区域，列出读本文前建议了解的内容

### ⚠️ 主题重叠必须双向跳转链接（强制，所有 Agent 必须遵守）

**当一篇文章提到的方法/算法/主题，在项目中已经有一篇专门的综述或精读覆盖时，必须在提到的地方加上指向那篇文章的跳转链接。** 这不是"最好加"，是强制要求。

具体执行方式：

1. **写作/编辑任何文章时，主动检查是否有更专门的文章覆盖当前提到的主题**。例如：写扩散模型综述时提到 PPO/GRPO 用于 VLA 的内容，必须检查项目里是否已有 [VLA On-Policy RL 方法综述](/论文综述/S12_VLA_On_Policy_RL方法综述) 这类专题文章，如果有，就在提到的地方加链接跳转过去。
2. **不能只在"相关阅读"区域加一次就完事**：正文中每次实质性提到那个主题时（不只是一笔带过的词汇），都应考虑加链接。至少要在"相关阅读"区、对比表格的对应行、以及"延伸阅读"区都加上链接，确保读者从任何入口都能跳转到那篇专题文章。
3. **反向链接同样要加**：如果 A 综述链接到了 B 专题文章，且 B 专题文章里还没链接回 A，应该在 B 文章的关联部分补上指向 A 的链接（双向可达）。
4. **判断标准**：如果删掉这条链接，读者在读到"这个方法还有很多变体/我该深入了解这个方向"时会找不到入口——那就必须加。
5. **这条规则适用于所有 Agent 在任何时候编辑或创建 Markdown 文章**，不只是在用户明确要求"加链接"的时候才执行。写完文章后要主动自查一遍：文中提到的每个已有专题文章的主题，是否都有对应跳转链接。

### 链接格式

跨目录用绝对路径：
```markdown
如果对 PPO 不熟悉，请先阅读 [策略梯度与 PPO](/前置知识/000a_前置知识_策略梯度与PPO)。
```

同目录用相对路径：
```markdown
更多细节参见 [DPPO 精读](./001_DPPO_扩散策略策略优化)。
```

### 行文中的自然引用

不要只在开头放链接，**正文中提到相关概念时也要加链接**：

```markdown
DPPO 的核心思路是对扩散过程的每一步应用 [PPO 的 clip 机制](/前置知识/000a_前置知识_策略梯度与PPO#53-ppoproximal-policy-optimization-2017)……
```

## 3.5 综述写作方法论（强制，最高优先级，所有 Agent 必须遵守）

### ⚠️⚠️⚠️ 综述禁止"逐篇罗列"，必须按分类或历史演进组织

**这是本项目所有综述文章（`论文综述/S*.md`）的最高优先级写作规则。违反这条规则的综述必须重写。**

**核心判断标准**：如果一篇综述读下来，读者的体验是"第一段讲论文 A 干了什么，第二段讲论文 B 干了什么，第三段讲论文 C 干了什么……每段之间只有标题变了，内容互相独立、没有对比、没有递进"——那这篇综述就是不合格的，还不如让读者直接去看这几篇论文的原文摘要。**综述存在的意义，是提供原文本身没有的、跨论文的结构性理解**——单篇论文精读做不到这件事，只有综述能做。

### 两种合法的组织方式（必须选择其中一种作为全文骨架）

**方式一：按方法论分类（Taxonomy）**

先问一个根本问题：这个领域要解决的核心矛盾/障碍是什么？然后把所有方法按"用什么思路绕开/解决这个障碍"划分成几条路线（通常 3-6 条），每条路线内部再讨论代表性方法之间的递进关系。

判断一个分类是否合格：
- 分类维度必须是**技术性的、可以画成决策树的**（如"要不要让梯度穿过多步生成链"、"要不要计算精确 log-prob"），不能是"方法 A 是这样、方法 B 是那样"这种同义反复的伪分类
- 同一条路线内的方法之间必须有**明确的递进/改进关系**（"方法 B 在方法 A 的基础上加了 X 来解决 Y 问题"），不能是简单并列
- 必须有一张贯穿全文的"路线全景图"（Mermaid），让读者一眼看到所有方法在整个技术图谱中的位置

**方式二：按历史演进（Evolution）**

如果一个领域的方法之间存在清晰的时间线式启发关系（后面的方法明确是为了解决前面方法暴露出的问题而提出的），可以按时间顺序组织，但**每一步演进都必须明确回答"前一个方法卡在哪里、这一步具体怎么解决"**，不能只是按发表时间排序然后逐个介绍。

### 强制自查清单（写完综述后必须逐条检查）

1. **开篇必须有"核心矛盾/障碍是什么"的明确陈述**，并且这个陈述奠定了全文的分类逻辑
2. **每一条分类路线/演进阶段，必须有至少一张对比表**，把该路线下的方法在关键维度上并排比较（不是简单堆砌方法名）
3. **每引入一个新方法，必须先说清楚它相对于同路线前一个方法（或路线本身要解决的核心矛盾）改进了什么**，不能孤立介绍"这个方法是什么"
4. **必须有一张全景 Mermaid 图**，展示所有方法在分类体系中的位置和相互关系
5. **必须有一张全景对比表**，横向对比所有涉及方法在若干个共同维度上的差异（而不是分散在各节里各自的小表格）
6. **必须有一张决策树或选型指南**，帮助读者根据自己的场景（数据量、是否有仿真环境、模型规模等）判断该选哪条路线
7. **禁止的反面模式**：连续两个二级标题分别是"## X 方法名 A"和"## Y 方法名 B"，中间没有任何承接、对比或递进的过渡文字——这就是"逐篇罗列"，必须重写
8. **单篇方法的技术细节应克制**：综述里每个方法的介绍篇幅应服务于"说明它在分类体系中的位置和贡献"，完整的公式推导、代码实现、实验数据表留给对应的论文精读文章（`论文综述/NNN_*.md`），综述里用一两个关键公式 + 链接过去即可，避免把综述写成"精读文章的简单拼接"

**判断标准（最终测试）**：读者读完这篇综述，应该能不看任何一篇原文，就说出"这个领域有 N 条主要技术路线，各自解决什么问题，彼此的取舍是什么，如果我遇到 XX 场景该用哪个"——如果读完只记住了"有 A、B、C、D 这几个方法"，说明综述没有达到及格线。

## 10. 系列文章

系列文章用于**长篇、多章节的系统性教程或深度专题**。与普通文章的区别：
- 首页/列表页只显示**一张卡片**（不是每章一张）
- 卡片上显示章节进度（如 `📖 2/5 章`）
- 左侧 sidebar 显示系列的完整章节目录
- 点击卡片进入系列概览页，再从概览页进入各章

### 10.1 目录结构

```
系列/
└── my_series_id/          # 系列 id（英文下划线命名）

    ├── 01_第一章标题.md
    ├── 02_第二章标题.md
    ├── 03_第三章标题.md
    └── ...
```

### 10.2 系列概览页 `index.md` 的 Frontmatter

```yaml
---
title: "系列标题：完整教程名"
order: 500                    # 在卡片列表中的排序
tags: [标签1, 标签2, 系列]
category: 系列               # category 设为 "系列"
star: 5
series:
  id: my_series_id           # 与目录名一致
  totalChapters: 5           # 总章节数（必须手动维护）
  dir: /系列/my_series_id    # 章节所在目录路径
---
```

### 10.3 系列概览页 `index.md` 的正文内容

概览页应包含：
1. 系列简介（为什么写这个系列、适合什么读者）
2. **完整章节目录**（带链接和一句话简介）
3. 前置知识要求
4. 学习建议/阅读顺序

示例：

```markdown
# 从零实现 ACT：完整工程系列

| 01 | [环境搭建](./01_环境搭建) | Isaac Lab 安装、数据采集硬件配置 |
```

### 10.4 章节文件的 Frontmatter

```yaml
---
title: "环境搭建"
series:
  id: my_series_id
  chapter: 1              # 章节编号，用于排序
order: 1                  # 也用于 sidebar 排序
---
```

章节文件**不需要**设置 `hidden: true`——它们在 `系列/` 子目录中，不会被 articles.data.mts 误扫描为独立卡片。

### 10.5 写系列文章的规范

系列文章的内容规范与普通文章完全一致（公式讲解、举例子、知识链接等），额外要求：

1. **每章开头有前情提要**：用 1-3 句话回顾上一章的结论，帮助读者衔接
2. **每章结尾有下章预告**：告诉读者下一步要解决什么问题
3. **每章独立可读**：虽然是系列，但每章应尽量自包含。读者跳读某一章时，不应因缺少上下文而完全看不懂
4. **交叉引用**：章节之间用相对链接互相引用（`./01_环境搭建`），引用外部知识用绝对链接
5. **totalChapters 必须维护**：新增或删除章节时，必须同步更新 `index.md` 中的 `series.totalChapters`

### 10.6 何时用系列 vs 普通文章

| 场景 | 选择 |
|------|------|
| 一个论文精读，5000 字左右 | 普通文章 |
| 一个概念讲解，3000 字 | 前置知识 |
| 一个完整工程项目教程，总计 2 万字以上 | **系列文章** |
| 一组相关论文的对比综述 | 普通综述 |
| 从零搭建某系统的完整过程，需要分步进行 | **系列文章** |
| 某技术的完整学习路径（如"从 Attention 到 VLA"） | **系列文章** |

## 11. 写作风格：直击本质，禁止绕圈子

### ⚠️⚠️ 最高优先级原则：简洁直接

**解释一个问题时，必须用最短路径直击本质。** 禁止为了"通俗"而堆砌废话、弱智比喻、重复解释。

具体要求：

1. **抓住问题的结构**：任何技术问题都有一个"骨架"——哪一步出了什么问题、用什么方法解决、为什么这个方法有效。把骨架写清楚就够了，不要在骨架外面裹一层又一层的"通俗解释"。
2. **禁止堆砌比喻和类比**：如果一个概念用数学语言 3 句话能说清，就不要用生活比喻绕 10 句话。读者有高中数学基础，知道什么是函数、什么是导数、什么是分段函数——直接用数学讲。
3. **禁止重复同一个意思**：说一遍就够了。不要用不同的措辞把同一件事翻来覆去地说。"一句话总结"之后又来一段"换句话说"——这就是废话。
4. **段落要有信息增量**：每一段必须提供新信息。如果删掉某一段不影响读者理解后续内容，那这一段就不该存在。
5. **不要预设读者是傻子**：读者是"不了解这个具体领域的聪明人"，不是"需要手把手哄着走的小孩"。尊重读者的智商，用精确的技术语言写作。

### 正确的解释模式

解释"为什么 X 不行 / 为什么要用 Y"时，正确的结构是：

```
1. X 的具体做法是什么（1-2 句）
2. 做法中哪一步出了问题（精确指出）
3. 问题的数学本质是什么（1-2 句）
4. Y 怎么绕过/解决这个问题（精确说明机制）
```

**不要**：先铺垫一段"你可能会问……"，再来一段比喻，再来一段"让我们用一个例子……"，再来一段"核心区别在于……"，再来一张对比表，再来一段"所以总结一下……"——同一个信息翻来覆去说了 6 遍，读者反而更晕。

### ⚠️⚠️ 缩写和术语：首次出现必须给出全称和一句话解释

**任何缩写、英文简写、领域术语，在文章中首次出现时必须同时给出：(1) 全称 (2) 一句话说明它是什么。** 之后再出现可以只用缩写。

**硬性规则**：

1. **禁止裸缩写**：不能直接写"VF"、"MC"、"AUC"、"CFG"而不解释。读者不一定知道 VF 是 Value Function、MC 是 Monte Carlo、AUC 是 Area Under ROC Curve、CFG 是 Classifier-Free Guidance。
2. **首次出现的格式**：`全称（缩写，一句话功能描述）`。例如：
   - ✅ "价值函数（Value Function, VF）——一个输入当前状态、输出'离任务完成还有多远'的打分网络"
   - ✅ "分类器无关引导（Classifier-Free Guidance, CFG）——通过对比'有条件'和'无条件'两路输出来增强生成质量的推理技巧"
   - ❌ "用 VF 给每帧打分"（读者：VF 是什么？）
   - ❌ "MC 估计比 bootstrap 方差更大"（读者：MC 是什么？）
3. **判断标准**：如果一个缩写不是"本科生肯定知道"的水平（如 GPU、CPU、API 这类不用解释），就必须在首次出现时展开。RL 领域的缩写（TD、MC、GAE、PPO、SAC、VF、CFG、AUC、MLP、MSE 等）全部需要首次展开——不能假设读者已经知道。
4. **每篇文章独立计算"首次"**：不能指望读者按顺序从第一篇读到当前这篇。每篇文章、每个章节都是独立入口，缩写在**每篇文章**中首次出现时都要展开。系列文章中，至少在每章首次出现时给出括号注释。
5. **代码变量名不替代解释**：代码里的 `v_hat`、`adv`、`mse` 不能指望读者自行破译。在代码块之前或之后的文字里，必须用中文明确说"这里的 `v_hat` 就是价值函数的预测输出 $\hat{V}(s_t)$"。

**反面例子（禁止）**：
> "用 VF 的 expected value 算 MC advantage，再取 percentile 做 binary labeling，配合 CFG dropout 训练。"

这句话对不了解这些缩写的读者来说完全不可读。

**正面例子（要求）**：
> "用训好的价值函数（VF）的期望输出 $\hat{V}(s_t)$，通过蒙特卡洛（MC）方式——即直接用轨迹跑完后的真实回报——计算优势 $A = R_t - \hat{V}(s_t)$，再取全局 30% 百分位阈值做二值化标签。"

### ⚠️⚠️ 结论先行，原理垂后（最高优先级，所有 Agent 必须遵守）

**任何概念/方法的讲解，必须先给最直白的结论性直觉，再给支撑这个结论的数学/原理依据。禁止反过来。**

这是一条比"先直觉再形式"更具体的排序规则，专门解决一种常见错误：Agent 为了显得严谨，习惯性地先铺垫理论依据（"这之所以可能是因为 XX 定理/性质……"），再引出结论。**这个顺序对读者来说是反的**——读者此刻最想知道的是"这东西到底是什么、解决了什么问题"，不是"支撑它成立的数学条件是什么"。先摆理论依据，读者会因为看不到目标而觉得莫名其妙、失去耐心，即使这段理论本身没有错。

**正确的写作顺序（强制）**：

1. **先给最直白的一句话结论**：这个方法本质上在做什么，用读者已经熟悉的东西打比方或直接说穿（如"就是重新训练一个新网络，直接学 A 到 B 的映射"）。
2. **再给这个结论解决了什么问题**：不用这个方法会怎样、错在哪。
3. **最后才给数学/原理依据**，且要明确标注为**可选**（如"补充（可跳过）"、放进折叠块、或拆到配套的推导详解文章里）——理论依据是用来"验证/加深"结论的，不是用来"推导出"结论给读者看的。读者读完 1、2 步应该已经完全理解这个方法，第 3 步是给想深挖的人看的。

**判断标准（自查）**：写完一段讲解后，删掉最后的理论依据部分，前面的内容是否依然能让读者完全明白"这个方法是什么、解决了什么问题"？如果答案是"能"，说明顺序对了；如果读者必须先读懂理论依据才能明白结论，说明顺序反了，必须调整。

**反面例子（禁止）**：
> "这件事之所以可能，是因为 PF-ODE（Probability Flow ODE，扩散/Flow 推理走的那条确定性微分方程）没有随机项——轨迹上任意一点已经唯一决定了终点（对比 SDE：有随机项时中间一点不足以确定终点）……[大段积分性质推导后]……所以 Consistency Model 可以训练一个新网络一步生成。"

↑ 禁止原因：读者要啃完一整段 ODE 性质才能等到"所以能一步生成"这个结论，而这个结论本身用一句话就能说清楚。

**正面例子（要求）**：
> "Consistency Model 就是重新训练一个新网络，直接学'随机噪声 → 最终动作'这一个映射，不需要中间步骤。训练它有两种办法：有教师网络就蒸馏（CD），没有就直接从数据训练（CT）。
>
> **补充（可跳过）**：这套技巧数学上说得通，是因为……[理论依据放最后，标注可跳过]"

### ⚠️ 推导过多时必须拆分正文与推导详解（强制）

**当一篇前置知识/精读/综述里，逐符号拆解 + 数值代入的公式详解密度过高、导致读者读一遍正文要不断被折叠块打断主线思路时，必须把完整推导拆分成一篇独立的配套"推导详解"文章，正文只保留结论、直觉和到详解的链接。**

**判断标准**：如果一篇文章里连续 3 个以上小节都是"结论一句话 + 大段公式详解折叠块"，且这些折叠块的内容主要是给"想验证细节"的读者看、不影响"想理解方法"的读者，就应该拆分。

**执行方式**：

1. **正文文章**：只保留"这个方法在解决什么问题、核心思路是什么、怎么用"，公式最多保留 1-2 个真正必须现场看到的（比如给出最终形式方便和别的方法对比），其余的完整推导链接到详解文章的对应小节锚点。
2. **推导详解文章**：文件名在正文文件名后加数字后缀（如 `000h_前置知识_XXX.md` → `000h2_前置知识_XXX公式推导详解.md`），frontmatter 的 `order` 取正文 `order` 加 0.5，`category` 仍为对应分类。开头必须注明"这篇是什么"和"先读正文再看这篇"。
3. **双向链接**：正文的"知识链接"区和每个跳过的小节末尾都要链接到详解文章的对应锚点；详解文章开头和结尾都要链回正文。
4. 详解文章本身仍需遵守本文件第 1 节和公式讲解相关的全部规则（可见摘要 + 折叠详解），只是它的读者群体和目的不同——正文追求"让人看懂"，详解追求"让人查证"。
