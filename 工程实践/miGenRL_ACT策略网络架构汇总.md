# miGenRL 策略网络架构汇总：一个 13.35M 参数的双臂灵巧手 ACT 变体

> `miGenRL` 是 embodied-arena 里负责"用示教数据训练操作策略、再让策略驱动仿真"的子系统。它的策略网络是一个 ACT（Action Chunking Transformer）变体，但相对原版 ACT 改动很大：CVAE 编码器按左右臂拆分、解码分成手腕与手指两级、观测走三通道深度掩码而不是 RGB、任务阶段通过一张 `nn.Embedding` 查表注入四个位置（注意：这是离散阶段标识专属的处理，本体状态 `qpos` 本身始终走的是线性投影，不查表）。本文把这个网络从输入张量到参数预算完整汇总一遍。

**本文的数字全部来自实测**，而非阅读代码后的推算：实例化 `ACTPolicy` 后统计 `sum(p.numel())`、并用 `torch.randn` 造 batch 跑一次前向，记录每个中间张量的形状。文中出现的 13.35M、144、146、6×8 这些数字都是这样得到的。

## 1. 贯穿全文的例子

全文以一份真实配置为准，所有形状和数字都对应它：

```text
配置        config/migenrl/stack_can_drawer_bimanual_base.yaml
任务        双臂把罐子放进抽屉（左手开抽屉、右手抓罐子，多阶段）
观测图像    3 路相机（head / left_wrist / right_wrist）× 3 通道深度掩码 × 90×120
本体状态    31 维（阶段索引 1 + 左臂 15 + 右臂 15）
动作        30 维 × 50 步 chunk
网络        hidden_dim=256, 场景编码器 2 层, 手腕解码器 4 层, nheads=4
参数量      13.35M（实测）
```

这个任务的关键特征是**多阶段**：先开抽屉、再抓罐子、再放入。网络必须知道"现在处于哪个阶段、当前该盯着哪个物体"，这就是后面反复出现的 `context` 张量存在的原因。

## 2. 整体架构

先看全景，再逐块拆。下图是整个网络的完整数据流，方框里标注了每处的张量形状和实测参数量。

<img src="/migenrl_architecture.png" alt="miGenRL ACT 策略网络总架构：从深度掩码输入到 30 维动作 chunk 的完整数据流，含 context 广播总线" class="img-full">

> 四条线索值得注意。**虚线部分只在训练时存在**：Dual CVAE Encoder 和真值动作输入，推理时隐变量直接置零。**底部的虚点总线**是 Task Context 真实的广播路径——同一个 embedding 表查出的向量顺着总线分四条支路接到 `action_encoder` / `state` / `query` / `action_head` 四个位置，标在每条支路终点，不是孤立存在的输入。**双臂各自持有独立的隐变量** `z_left`、`z_right`，不是共享一个 z。**解码是两级串行的**：Dual-Arm Wrist Decoder 的 query 由"时间步 ⊕ 臂身份"两部分组成（100 = 50 步 × 2 臂），先出手腕动作，再作为 memory 喂给 Hand Cross-Attn Decoder，手指以手腕为条件生成。

这里有个容易看漏的实现细节：`ACTPolicy` 构造时如果检测到动作布局里含手部分量，会把传给底层 DETR-VAE 的 `action_dim` 从 30 **改写成 18**。也就是说 DETR-VAE 自己从头到尾只知道手腕的 18 维，完全不知道手指的存在；手指的 12 维由外挂的解码器补齐，最后在 `ACTPolicy` 这一层拼回 30 维。理解这一点，后面所有"为什么每只臂的动作头输出 9 维"之类的问题就都自洽了。

## 3. 输入侧：三个张量的索引布局

这一节讲清楚三个输入张量每一位是什么。索引布局是后面损失加权、动作拆分、参考系解码的共同基础，读错一位后面全错。

### 3.1 动作的 30 维布局

动作维度不是随意排的，`action_layout.py` 里写死了一张表。30 维对应的布局是：

| 切片 | 内容 | 归属 |
|------|------|------|
| `[0:3]` | 左腕位置 | 手腕段 |
| `[3:9]` | 左腕 rot6d | 手腕段 |
| `[9:12]` | 右腕位置 | 手腕段 |
| `[12:18]` | 右腕 rot6d | 手腕段 |
| `[18:24]` | 左手 6 维隐变量 | 手指段 |
| `[24:30]` | 右手 6 维隐变量 | 手指段 |

排列顺序是**先双臂手腕、再双手手指**，不是"左臂全部、右臂全部"。这样"手腕 18 维"正好是连续切片 `[0:18]`，手部解码器可以直接切出来用，不需要做跨段的索引拼接。

手指为什么是 6 维而不是真实的 22 个关节角？因为数据侧先用 PCA 把 22 维手指关节压成了 6 维隐变量（`hand_synergy`），网络预测隐变量，执行时再解码回 22 维。这一步的完整数学原理见 [主成分分析 PCA](/前置知识/002j_前置知识_主成分分析PCA)，在 miGenRL 里的具体拟合流程见[系列第 04 章](/系列/stack_can_drawer_migenrl_deep_dive/04_hand_synergy_PCA降维)。

### 3.2 本体状态的 31 维布局与奇数维拆分

`qpos` 是 31 维：1 维阶段索引 + 左臂 15 维 + 右臂 15 维（每臂 = 位置 3 + rot6d 6 + 手指隐变量 6）。

31 是奇数，没法对半分给两只臂。代码的处理办法是**把第 0 维的阶段索引复制给两边**：

```python
# _split_dual_arm_qpos，qpos.shape[-1] 为奇数时
phase = qpos[..., :1]                      # 阶段索引，两臂共享
side_dim = (31 - 1) // 2                   # 15
left  = cat([phase, qpos[..., 1:16]])      # 16 维 → 左臂专属 Linear(16→256)
right = cat([phase, qpos[..., 16:31]])     # 16 维 → 右臂专属 Linear(16→256)
```

阶段索引被**复制**而不是分割，所以两个 16 维视图加起来是 32 而非 31。两只臂各自的编码器都能看到"现在是第几阶段"，但只能看到自己那半边的位姿。

这个设计的动机是双臂在多阶段任务里必须共享阶段信息（左手开抽屉的时机取决于右手抓没抓到罐子），但位姿信息隔离能让每只臂的投影层专注学自己的运动学分布。

### 3.3 三通道深度掩码图像

观测不是 RGB，而是人工构造的三通道张量。每个通道的语义是固定的：

| 通道 | 内容 | 构造方式 |
|------|------|----------|
| 0 | 深度 | 只保留任务物体的深度，按实例做 min-max 归一化到 [0,1]，其余置 0 |
| 1 | 机器人与在手物体掩码 | 分割图里属于机器人或已抓起物体的像素置 1 |
| 2 | 目标物体掩码 | 分割图里属于**当前阶段目标**的像素置 1 |

三个通道都先和同一个 `keep` 掩码取交集，`keep` 的定义是"属于配置里声明的任务物体、深度有限、且距离不超过 `depth_mask_max_distance_m`（该配置里是 1.5 米）"。桌面、背景、未声明的几何体一律不进入模型输入。

通道 2 是**随阶段动态变化**的：开抽屉阶段目标是抽屉，抓罐子阶段目标是罐子。这由 `depth_mask.dynamic_roles` 打开，按 `phase_index` 查表决定当前该把哪个物体标进通道 2。

为什么费这么大劲做掩码而不直接喂 RGB？两个原因。一是**泛化**：去掉纹理、光照、背景后，策略只能依赖几何和物体身份，换个桌布或换个光照不会让它崩。二是**多阶段消歧**：通道 2 显式告诉网络"这一刻该操作谁"，否则网络得从 RGB 里自己猜当前阶段，这是个额外的、没必要的学习负担。

代价是训练和推理两条路径必须严格对齐——训练时从 HDF5 里的深度图加分割图离线构造，推理时从仿真的深度传感器加实例分割在线构造。两边只要有一处语义不一致（比如推理时把桌子算进了 `keep`），策略立刻失效。这也是项目里专门设一份 `depth_mask_schema.py` 集中管理标签语义的原因。

### 3.4 context 张量

`context = [frame_id, phase_index]`，2 维浮点。`frame_id` 是当前参考系物体在场景物体列表里的序号，`phase_index` 是任务阶段编号。网络只用它做 embedding 查表，不做数值运算。

## 4. 视觉分支：144 个 token 是怎么来的

三路相机共享**同一套** CNN 权重（`self.backbones[0]`，代码里带 `# HARDCODED` 注释），逐相机前向。

默认骨干不是 ResNet，而是自定义的 `SimpleCNN`：四个 stage，每个 stage 两层 3×3 卷积配 `GroupNorm`，通道数 64→128→256→512。配置里 `backbone_output_stride=16`，所以取 `layer3` 的输出，通道数 256。

实测单相机输出形状：

```text
输入 [B,3,90,120] → SimpleCNN layer3 → [B,256,6,8]
```

90/16≈6、120/16≈8，对得上。接着 1×1 卷积把通道投到 `hidden_dim=256`（这里恰好同为 256，投影仍然存在），加上一个逐相机的可学习偏置 `camera_embed`，然后**沿宽度维拼接**三个相机：

```text
head        [B,256,6,8]  ┐
left_wrist  [B,256,6,8]  ├─ 沿 width 拼接 → [B,256,6,24] → flatten → [B,144,256]
right_wrist [B,256,6,8]  ┘
```

6×24 = 144，这就是实测到的视觉 token 数。三个相机被"横向摊平"成一张宽图，而不是各自独立成组。

这种拼法有个直接后果：位置编码是二维正弦编码，按拼接后的 6×24 网格生成。也就是说 head 相机的最右列和 left_wrist 相机的最左列在位置编码上是**相邻**的，尽管物理上毫无关系。区分相机靠的是加上去的 `camera_embed` 偏置（初始化为全零，训练中自行学出差异），不是位置编码。

`camera_embed` 初始化为零是个刻意选择：网络起步时三个相机的特征完全等价，训练过程再根据任务需要长出区分度。这样加载不含该参数的旧 checkpoint 也能平滑兼容（代码里确实有这条兼容分支）。

## 5. CVAE 编码器：为什么要按臂拆开

CVAE 编码器**只在训练时工作**。它读入真值动作序列，压出一个隐向量 $z$，作用是告诉解码器"这条轨迹属于哪种风格"。推理时没有真值动作，$z$ 直接置零。

miGenRL 的改动是：左右臂各有一套完全独立的编码器参数。以左臂为例，一次编码经过的步骤是：

| 步骤 | 操作 | 输出形状 |
|------|------|----------|
| 1 | 左臂动作序列过 `Linear(9→256)` | `[B,50,256]` |
| 2 | 左臂 qpos 过 `Linear(16→256)` | `[B,1,256]` |
| 3 | 拼上左臂专属 CLS token | `[B,52,256]` |
| 4 | 过 2 层 Transformer 编码器 | `[B,52,256]` |
| 5 | 只取 CLS 位置的输出 | `[B,256]` |
| 6 | 过 `Linear(256→64)` 切成两半 | `mu`、`logvar` 各 `[B,32]` |
| 7 | 重参数化采样 | `z_left [B,32]` |

序列长度 52 = 1 个 CLS + 1 个 qpos + 50 步动作。每臂动作是 9 维（位置 3 + rot6d 6），因为如第 2 节所说，DETR-VAE 眼里的动作维度是 18，对半分给两臂就是 9。

两臂的 `mu`、`logvar` 各 32 维，拼起来向外报 64 维，KL 项在这 64 维上统一算。

**为什么不把双臂动作拼一起编成一个隐向量**：这个任务里两只手做的是性质不同的事——左手开抽屉是低精度大幅位移，右手抓罐子是高精度小幅调整。两者的"风格"分布不相关。硬塞进同一个隐向量，隐空间要同时表达两种无关的变化模式，KL 正则又要求这个混合分布贴近标准正态，两个目标互相拖累。拆开之后每个隐向量只需描述一只手的变化模式。

KL 项本身用的是高斯闭式解，是标准写法没有定制，推导见 [对数似然与变分下界](/前置知识/000e_前置知识_对数似然与变分下界)；采样处的可导性处理见 [重参数化技巧](/前置知识/002e_前置知识_重参数化技巧)。

## 6. 手腕解码器：146 个 memory token 与双臂并行

### 6.1 memory 的构造

每只臂拿到一份自己的 memory，长度 146：

```text
[0]      该臂的 latent token   ← z 投影到 256 维
[1]      该臂的 qpos token     ← 该臂 16 维 qpos 投影到 256 维
[2:146]  共享视觉 token        ← 第 4 节的 144 个
```

两臂的前两个 token 各不相同（各自的 $z$ 和各自的位姿），后 144 个视觉 token 完全共享——两只手看到的是同一个场景。

位置编码上，前两个 token 用一张 4 行的可学习表：左臂取第 0、2 行，右臂取第 1、3 行。这样"左臂的 latent"和"右臂的 latent"有不同的位置标识，即使它们在序列里都排在下标 0。

### 6.2 一个容易忽略的计算成本

`_decode_from_memory` 对每只臂做的事是：**先跑一遍场景编码器，再跑解码器**。两只臂就是各跑一遍：

```text
左臂 memory [B,146,256] → 场景编码器(2层) → 手腕解码器(4层, 左 query) → [B,50,256] → 左头 → [B,50,9]
右臂 memory [B,146,256] → 场景编码器(2层) → 手腕解码器(4层, 右 query) → [B,50,256] → 右头 → [B,50,9]
                                                                          拼接 → [B,50,18]
```

编码器和解码器的**权重是共享的**（两次都用同一个 `self.transformer`），但**前向被执行了两次**。共享参数省显存，重复前向费算力。

这是个明确的取舍：如果两臂用完全独立的 Transformer，参数量直接翻倍；现在的做法是参数共享、通过不同的 query 和不同的前两个 memory token 来区分左右。代价是每个训练步的注意力计算量翻倍。

### 6.3 Query 的构造

每臂的 50 个 Action Query 由两部分相加得到：

```python
left_query  = time_query_embed.weight + arm_query_embed.weight[0]   # [50,256]
right_query = time_query_embed.weight + arm_query_embed.weight[1]
```

`time_query_embed` 是 50 行的表，编码"我是 chunk 里的第几步"，两臂共享。`arm_query_embed` 是 2 行的表，编码"我属于哪只臂"。相加而不是拼接，所以维度保持 256。

这个分解是有意义的：50 个时间步的"步序语义"对两只手是通用的（第 3 步总是比第 40 步更接近当前时刻），只有臂身份需要区分。用加法分解可以让时间步表征在两臂之间共享统计强度。

顺带一个实测发现：原版 ACT 的 `self.query_embed`（50×256 = 12800 个参数）在双臂路径下**被分配但从未使用**。同样闲置的还有单臂路径的一整套投影层，合计约 5.9 万参数。占比很小，但确实是死重。

## 7. 手部解码器：让手指对齐手腕

### 7.1 设计动机

手腕要去哪，主要由视觉场景决定——看到罐子在哪就知道手往哪伸。手指该张多大，主要由**手腕此刻在做什么**决定——正在接近时要张开，已经贴上了才能合拢。后者是一种对手腕动作的从属关系。

如果让同一组 Action Query 直接输出 30 维（手腕 + 手指），手指的预测和手腕的预测是**并列**产生的，网络只能隐式地希望两者协调。miGenRL 的做法是把这个从属关系显式建成一次交叉注意力：手腕动作先生成，手指的 query 再去"看"这些手腕动作。

### 7.2 逐时间步对齐是关键

这个解码器最值得看的一行是 cross-attention 前的 reshape。手部 query 的形状是 `[B,50,256]`，手腕 token 的形状是 `[B,50,2,256]`（每个时间步 2 个 token：位置和 rot6d 各投影一个）。做交叉注意力时：

```python
aligned_query  = hand_query.reshape(B * 50, 1, 256)      # 每个时间步单独成一个"batch"
aligned_memory = wrist_tokens.reshape(B * 50, 2, 256)
attended, _ = cross_attention(aligned_query, aligned_memory, aligned_memory)
```

把时间维折进 batch 维，意味着第 $t$ 步的手指 query **只能看到第 $t$ 步的手腕动作**，看不到 $t-1$ 或 $t+1$ 步。注意 reshape 后 query 的序列长度是 1、memory 的序列长度是 2——每个"样本"就是一个时间步，注意力只在该步的两个手腕 token（位置、rot6d）之间分配。这是严格的逐步对齐，不是对整段手腕轨迹做注意力。

这个选择很关键，也和直觉相反：为什么不让手指看到整段手腕轨迹，那样信息更多？因为手指和手腕的物理耦合本来就是**同时刻**的——第 20 步手腕贴到罐子表面，第 20 步手指就该合拢，让它去看第 5 步手腕在哪没有帮助，只会引入噪声和无谓的注意力参数。跨时间步的协调则由每个 block 里的 self-attention 负责（self-attention 作用在 `[B,50,256]` 上，能看到整段序列）。

所以每个 block 的结构是"先 self-attention 看整段、再 cross-attention 对齐单步、最后 FFN"，三个子层各配一次 LayerNorm 和残差：

| 子层 | 作用域 | 负责什么 |
|------|--------|----------|
| self-attention | 整段 50 步 | 跨时间步协调开合节奏 |
| cross-attention | 单个时间步 | 对齐同一时刻的手腕动作 |
| FeedForward（1024, GELU） | 逐 token | 非线性变换 |

关于 cross-attention 里 Q/K/V 各自的角色，见 [Cross Attention 与交替注意力机制](/前置知识/001e_前置知识_Cross_Attention与交替注意力机制)。

### 7.3 query 的初值来自哪

手部 query 不是纯粹的可学习参数，而是"可学习的时间步 embedding + 当前状态特征"之和。这里必须分清楚三样东西各自的来路：`qpos`（31 维原始向量，**不经过任何查表**）、一个轻量卷积编码的图像特征（同样是连续向量），两者与 `phase_index` 查表得到的 16 维 embedding（这一项才是真正的 `nn.Embedding` 查表）拼接在一起，再整体过一次线性投影，得到共享状态特征。这个共享状态特征之后才和查表得到的时间步 embedding 相加，组成最终的 query。

也就是说手部解码器有**自己独立的一套图像编码器**，不复用主干的 CNN。它很小（约 1.9 万参数，两层 stride-2 卷积后池化到 2×2），只需要提供粗粒度的场景线索。这个设计避免了让手部解码器依赖主干那 144 个高分辨率视觉 token——手指要的信息量本来就少。

### 7.4 左右手完全独立

`side_blocks` 是一个 `ModuleDict`，左右手各有一套 2 层的 block，参数不共享。左手 query 只看左腕动作，右手只看右腕。两手各输出 6 维，拼成 12 维。

这里是整个网络参数量最大的单块——两侧合计约 421 万参数，和 4 层手腕解码器几乎持平。原因是每个 block 含两个多头注意力加一个 1024 维的 FFN，而且左右不共享，等于 4 个这样的 block。

### 7.5 拼回 30 维

手腕 18 维和手指 12 维产出后，按第 3.1 节的固定布局重排。代码用一个预先算好的索引表做 `index_select`，不是手工切片拼接：

```python
compact = cat([wrist_18, hand_12])           # [B,50,30]，顺序是 腕腕手手
return compact.index_select(-1, restore_indices)  # 重排到标准布局
```

`restore_indices` 在构造函数里根据动作布局表反解出来。这样布局表一改，索引自动跟着变，不需要改前向代码。

## 8. 损失函数

### 8.1 总损失

总损失是加权 L1 加 KL，KL 权重为 1。KL 部分是标准高斯闭式解（见[对数似然与变分下界](/前置知识/000e_前置知识_对数似然与变分下界)），本节只讲 miGenRL 定制的加权 L1。

### 8.2 加权 L1 与 query 衰减

这是本文唯一需要展开的公式，因为它把两种彼此独立的加权机制乘在了一起，光看文字容易搞混谁乘谁。

$$
\mathcal{L}_{L1} = \frac{\sum_{b,t,d}\; w_d \cdot e^{-\gamma t} \cdot \bar{m}_{b,t} \cdot \lvert a_{b,t,d} - \hat{a}_{b,t,d}\rvert}{\sum_{b,t,d}\; w_d \cdot e^{-\gamma t} \cdot \bar{m}_{b,t}}
$$

**这个公式在做什么**：算预测动作和真值的绝对误差，但给每一项乘两个折扣——按动作维度的重要性打分、按这一步在 chunk 里有多靠后打折，最后做加权平均而不是简单平均。

::: details 📐 公式详解（点击展开）

| 子表达式 | 它是谁 | 它在干嘛 |
|---------|--------|---------|
| $\lvert a_{b,t,d}-\hat{a}_{b,t,d}\rvert$ | **原始误差** | 第 $b$ 个样本、chunk 第 $t$ 步、第 $d$ 维，真值和预测差多少 |
| $w_d$ | **维度重要性** | 按维度类型查表：位置 4.0、rot6d 3.0、手指隐变量 8.0 |
| $e^{-\gamma t}$ | **远期折扣** | $t$ 越靠后权重越小；$\gamma$ 是 `query_loss_decay`，基础预设为 0 即不折扣 |
| $\bar{m}_{b,t}$ | **有效位闸门** | padding 取反，填充步直接乘 0 |
| 分母 $\sum w_d e^{-\gamma t}\bar{m}$ | **归一化器** | 用实际生效的权重总和归一，而不是除以元素个数 |

**用人话读**："把每个预测误差按'这一维有多重要'和'这一步有多远'两重打折，加起来，再除以打折后的权重总和。"

**为什么分母要用权重和而不是计数**：如果分母固定为元素个数，那么把某一维的权重从 4 调到 8，总损失的数值量级会整体抬升，学习率就得跟着重调。用权重和归一后，权重表只改变各维之间的**相对**重视程度，损失的绝对量级保持稳定，调权重不用动学习率。

**去掉 $e^{-\gamma t}$ 会怎样**：50 步全部等权。chunk 末尾那些步在推理时几乎总会被后续新预测覆盖掉（见第 9 节），花同等力气去拟合它们，等于把容量浪费在不会被执行的动作上。开了衰减后，网络优先保证近端几步准确。
:::

### 8.3 手指权重为什么是 8.0

权重表里手指隐变量 8.0，明显高于位置 4.0 和旋转 3.0。这是 PCA 降维的直接后果。

PCA 分量按方差排序，把 22 维手指关节空间压进 6 维后，隐空间里一个很小的数值变化，经解码矩阵放大可能对应手指关节上相当大的角度变化。如果不加权，网络会发现"把误差预算花在数值尺度天然更大的位置维度上，总损失降得更快"，于是相对忽视手指——而手指姿态恰恰是抓取成不成功最敏感的部分。8.0 的权重是对这个尺度失衡的补偿。

代入具体数字：某手指维绝对误差 0.02，某位置维绝对误差 0.05。加权后贡献分别是 $8.0\times0.02=0.16$ 与 $4.0\times0.05=0.20$。位置维的原始误差是手指维的 2.5 倍，加权后两者对总损失的贡献变得可比，手指不会被淹没。

### 8.4 分组监控指标

除了总损失，训练时还会按动作分组算出一批只读的 L1 指标：`l1_left_pos`、`l1_right_rot6d`、`l1_left_gripper` 等，加上手腕整体和手部整体各一项。这些不参与反向传播，纯粹用于诊断——训练曲线整体下降但抓取仍然失败时，能直接定位是手腕轨迹不准还是手指开合不准。

## 9. 推理侧：时间聚合

训练时网络一次输出 50 步，推理时却每步都重新预测一遍。于是同一个物理时刻会被多个 chunk 各自预测一次——第 100 步的动作，可能在第 100 步、第 99 步、第 98 步……分别被预测过。直接只用最新那次预测，动作会在相邻步之间跳变。

时间聚合的做法是把落在同一时刻的所有预测做指数加权平均。实现方式是维护两个缓冲区（动作累加和、权重累加和），每来一个新 chunk 就先把旧值乘上衰减因子 $e^{-\lambda}$，再把新预测加进去：

```python
decay = math.exp(-temporal_aggregation_decay)   # 配置里 λ=0.05 → decay≈0.951
action_sum[env, t:t+50]    *= decay             # 旧的先打折
weight_sum[env, t:t+50]    *= decay
action_sum[env, t:t+50]    += new_chunk         # 新的加进来，权重 1.0
weight_sum[env, t:t+50]    += 1.0
executed_action = action_sum[env, t] / weight_sum[env, t]   # 取用时归一
```

每来一个新 chunk 就整体打一次折，意味着一个 $k$ 步前产生的预测，此刻的相对权重是 $e^{-\lambda k}$。

![不同衰减系数下历史预测权重随年龄的衰减](/migenrl_temporal_aggregation_weights.png)

> 蓝线是 miGenRL 的默认值 0.05，半衰期约 14 步——十几步前的旧预测仍有一半话语权，所以动作相当平滑。红线 0.30 半衰期约 2 步，基本等于只听最新预测。绿线 0.01 接近均匀平均，平滑但反应迟钝。

这里的取舍很直接：衰减小则平滑但迟钝（场景变了还在被旧预测拖着），衰减大则灵敏但抖。0.05 是在这个任务上试出来的折中。

一个实现细节：旋转部分如果用四元数表示，聚合前要做符号对齐（$q$ 和 $-q$ 表示同一旋转，直接平均会互相抵消）。代码里通过 `quaternion_ranges` 检查新旧预测的点积，为负就翻转符号。该配置用 rot6d 而非四元数，这段逻辑不触发，但对切换到四元数表征的配置是必要的。

| 模块 | 参数量 | 占比 | 推理时是否参与 |
|------|--------|------|----------------|
| 手腕解码器（4 层，双臂共享） | 4,214,272 | 31.6% | 是 |
| 手部交叉注意力解码器（2 块 × 2 侧） | 4,213,760 | 31.6% | 是 |
| 场景编码器（2 层） | 1,579,520 | 11.8% | 是 |

几个值得注意的读数：

**手部解码器的体量与主解码器持平**。它只负责 30 维里的 12 维，却吃掉三分之一参数。原因是左右手不共享参数，每侧 2 个 block、每个 block 含两个注意力加 1024 维 FFN。如果让左右手共享这套 block（用 side embedding 区分），能省下约 210 万参数。是否值得取决于两只手的抓握模式差异有多大，这个任务里左手主要开抽屉、右手主要抓取，差异确实大，不共享有其道理。

**CVAE 编码器是纯训练开销**。1.58M 参数在推理时完全空转。部署时可以从 checkpoint 里剥掉，代码里没有做这个优化，因为同一份 checkpoint 还要支持 resume 训练。

**场景编码器和 CVAE 编码器参数量完全相同**（都是 1,579,520）。因为两者都是 2 层、`hidden_dim=256`、`dim_feedforward=1024` 的同构 Transformer 编码器，只是各自独立实例化了一份。

## 11. 条件注入：一个 embedding 进四个位置

`context` 里的 `frame_id` 查一张 `nn.Embedding(3, 256)` 表得到 256 维向量，同一个向量被加到四个位置（对应总架构图里的四个 C 标记）：

| 注入点 | 配置名 | 影响什么 |
|--------|--------|----------|
| CVAE 编码器的动作与 qpos token | `action_encoder` | 怎么编码轨迹风格 |
| memory 里的 qpos token | `state` | 怎么理解当前状态 |
| 解码器的 Action Query | `query` | 查询时关注什么 |
| 解码器输出的 hidden state | `action_head` | 直接偏移最终动作预测 |

`num_embeddings` 不是拍脑袋定的，而是等于场景物体列表的长度——由 `policy_context_num_embeddings` 从环境配置里读出物体数量算得。该任务里是 3（罐子、抽屉、桌子）。

为什么要注入四次而不是一次？条件信号在多层网络里逐层传递会被稀释，网络可能在中间层"忘记"当前阶段。在每个关键计算节点都直接注入，保证条件始终可用。这类多点注入在条件生成网络里是常规做法（对比 [条件约束的 ACT 模型](/工程实践/条件约束的ACT模型) 里讨论的其他注入方案）。

框架里还预留了第五个注入位置 `norm`——通过 FiLM 式的 scale/shift 调制每个 LayerNorm 的输出（`_apply_norm_context`，投影层权重初始化为零使其起步时等价于恒等变换）。但固定预设只启用了 `state / query / action_head / action_encoder` 四处，`norm` 通路的投影层实测为 `None`，即完全未启用。

需要注意注入表用的是 `frame_id`，而手部解码器用的是 `phase_index`（自己一张 16 行的表）。两个条件信号来源不同、embedding 表不同、维度不同（256 对 16），不要混淆。

## 12. 架构里的休眠开关

`DETRVAE` 的构造函数接受一批开关，固定预设下全部关闭。实测确认它们均为 `None`：

| 开关 | 功能 | 预设状态 |
|------|------|----------|
| `predict_hand_gate` | 额外输出 2 维手部开合门控 logits | 关（`hand_gate_head` 为 `None`） |
| `interact_segment_layers` | 双臂交互编码器，输出残差修正动作 | 关（`interact_encoder` 为 `None`） |
| `visual_fusion_type: bfa` | 按状态给多相机特征动态加权 | 关（用 `concat`） |
| `norm_context_dim` | LayerNorm 的 FiLM 式条件调制 | 关（投影层为 `None`） |
| `inference_latent` | 推理时用非零 $z$（可固定、可随机、可分左右） | 关（$z$ 置零） |

其中 BFA（Best-Feature-Aware Fusion）值得一提：它用一个小网络根据当前 `qpos` 给三个相机打分，softmax 后乘回特征，让网络能"选择性地信任某个视角"。输出层权重初始化为零，起步时三相机等权，等价于关闭状态。这类"初始化为恒等变换的可选模块"是安全添加新结构的常规手法——开启后不会立刻破坏已训好的行为。

`interact_residual_head` 同样用了零初始化（`_zero_last_linear`），启用后初始残差为零，动作预测不受影响，训练中再逐渐长出修正量。

这些休眠开关说明这套代码是实验平台而非固定产品。但要注意：`FIXED_POLICY_CONFIG_KEYS` 把这些键全部列为**禁止在 YAML 里配置**，一旦出现就直接报错。想启用必须改 `ACT_POLICY_PRESETS` 里的预设或加新预设。这是刻意的设计约束——保证同一个预设名在任何配置下都对应完全相同的网络结构，实验结果可比。

框架提供的预设有四个：

| 预设 | 改动 |
|------|------|
| `base` | 默认：hidden 256、enc 2、dec 4、nheads 4 |
| `depth_mask_dual_stream` | 换 `depth_mask_cnn` 主干（深度与掩码分双支流后融合），stride 8 |
| `base_query_decay` | 开启 `query_loss_decay=0.05` |
| `large_query_decay` | hidden 384、FFN 1536、enc 3、dec 6、nheads 8，且开启衰减 |

## 13. RL 阶段：一个尺寸不匹配的接口

BC 训练完之后，框架提供了 PPO 微调路径（`act_ppo_trainer.py`）。它把训好的 ACT 当 actor，外接一个只看 `qpos` 的两层 Tanh MLP 作为 critic，动作分布用对角高斯（`log_std` 是可学习参数，初值 $-2.0$）。

RL 目标里有四项：PPO 的 clip 目标、价值损失（带 clip）、熵正则，再加一个**锚定损失**——把当前 actor 的输出往冻结的 BC 初始副本上拉，防止 RL 把预训练策略拽跑。还可选混入专家数据重放，直接算 BC 损失一起优化。PPO 本身的 clip 机制见 [策略梯度与 PPO](/前置知识/000a_前置知识_策略梯度与PPO)；同类 BC→RL 后训练的对照实现见 [RLinf BC 到 RL 的 ACT 后训练架构](/工程实践/RLinf_BC到RL的ACT后训练架构)。

有一处必须点明的接口问题。`ActPPOPolicy.action_mean` 这样调 actor：

```python
pred = self.actor(norm_qpos, images)     # 没有传 context
if pred.ndim == 3:
    pred = pred[:, 0]                    # 50 步 chunk 只取第 1 步
```

它不传 `context`。但本文这套双臂灵巧手配置的手部解码器**强制要求** `context`——`_shared_features` 里明确写着缺失就抛异常。实测确认了这一点：不带 `context` 调用会直接报 `ValueError: The fixed hand-query decoder requires frame and phase policy context`。

也就是说这条 PPO 路径与本文这套带手部解码器的配置**目前不兼容**。它适用的是不含手部分量的动作布局（此时 `hand_query_decoder` 为 `None`，不需要 `context`）。另外注意 `pred[:, 0]` 把 50 步 chunk 压成单步——RL 阶段退化成单步策略，`rollout.action_execution` 也被强制改成 `single_step`，chunk 机制在 RL 阶段整体让位。

这不是需要立刻修的 bug（两条路径服务不同配置），但如果要给本文这套配置做 PPO 微调，必须先把 `context` 沿调用链传下去。

## 14. 与相关方案的对比

| 维度 | 原版 ACT | miGenRL ACT | InterACT | 条件约束 ACT |
|------|----------|-------------|----------|--------------|
| 观测 | RGB 多相机 | 三通道深度掩码 | RGB | RGB + 语言 |
| CVAE 编码 | 单套，双臂合编 | 左右臂各一套 | 单套 | 单套 |
| 解码结构 | 一组 query 出全部动作 | 手腕/手指两级串行 | 分层交替注意力 | 一组 query |
| 双臂协调 | 隐式（同一序列） | memory 共享 + query 区分 | 显式跨臂注意力 | 隐式 |
| 手指表示 | 原始关节角 | PCA 6 维隐变量 | 原始关节角 | 原始关节角 |
| 条件注入 | 无 | frame_id 注入 4 处 | 无 | 语言 token |
| 参数量 | ~80M（ResNet18 主干） | 13.35M | — | — |

参数量差距主要来自主干：原版 ACT 用 ResNet18（约 1100 万参数，且每个相机一份），miGenRL 用自定义 `SimpleCNN` 且三相机共享，主干只占 1.15M。深度掩码输入本身信息密度高、纹理少，不需要 ImageNet 预训练的大主干。

更多双臂协调方案的对比见 [InterACT 与 ACT 的区别解析](/工程实践/InterACT与ACT的区别解析) 和 [双臂任务训练方法研究](/工程实践/双臂任务训练方法研究)。

## 15. 小结

miGenRL 的策略网络是一个 13.35M 参数的 ACT 变体，相对原版有五处实质改动：

1. **观测换成三通道深度掩码**——深度、机器人掩码、当前阶段目标掩码，训练与推理两条路径严格对齐，为的是泛化能力和多阶段消歧。
2. **CVAE 编码器按左右臂拆分**——两只手做性质不同的事，共用隐向量会让隐空间语义混杂、KL 正则失效。
3. **手腕与手指两级解码**——手指的 query 逐时间步交叉注意力对齐手腕动作，把"手指从属于手腕"这个物理关系显式建模；跨步协调交给 self-attention。
4. **手指经 PCA 压到 6 维**，并用 8.0 的高损失权重补偿降维带来的数值尺度失衡。
5. **任务阶段通过 embedding 注入四个位置**，防止条件信号在层间稀释。

工程上有三处值得记住的取舍：双臂共享 Transformer 权重但前向跑两次（省参数、费算力）；手部解码器左右不共享，吃掉三分之一参数；CVAE 编码器 1.58M 参数推理时纯空转。

架构里还留着五个休眠开关（手部门控、双臂交互编码器、BFA 视觉融合、LayerNorm 条件调制、非零推理隐变量），全部零初始化以保证启用时不破坏既有行为，但被 `FIXED_POLICY_CONFIG_KEYS` 禁止从 YAML 配置，只能通过预设启用——这是为了让预设名与网络结构严格一一对应，保证实验可比。
