## “π₀.₇”在这个仓库里是什么意思

项目名称容易造成误读。Physical Intelligence 官方公开的 OpenPI 仓库在这份源码快照中实现的是 π₀、π₀-FAST 和 π₀.₅；`ModelType` 仍然使用 `PI0`、`PI0_FAST`、`PI05` 三种类型。这个项目没有把模型类型改成官方的 `PI07`，而是在 `src/openpi/` 中保留 π₀.₅ PyTorch 路径，再把 G1 采集、训练和部署能力接到它周围。

因此，“π₀.₇-inspired”描述的是组合方案：

| 层次 | 项目采用的实现 | 解决的问题 |
|------|----------------|------------|
| 模型骨干 | PaliGemma 前缀 + 连续 Flow Matching Action Expert | 从视觉、语言和状态生成动作块 |
| 机器人接口 | G1 43 DoF、双 Dex3-1、三路 RGB | 把具体硬件变成稳定的数据契约 |
| 训练扩展 | FAST teacher-forcing、subtask、Knowledge Insulation | 同时学习阶段文字和连续控制，避免分支互相污染 |
| 推理扩展 | RTC 硬前缀、异步动作缓存、滚动重规划 | 在远程推理延迟下保持动作连续 |
| 可靠性层 | episode QC、mask、关节限位、急停和状态新鲜度 | 阻止脏数据或过期动作到达机器人 |

对“拿起箱子”任务来说，模型只负责根据当前观察提出一个动作块；它不负责理解 ROS2 消息、求解机械臂逆运动学（Inverse Kinematics, IK——把末端位姿转换成关节角的数值过程），也不负责决定一个危险命令是否可以发送。那些职责属于模型外部的工程层。

## 一次动作的完整生命周期

下面的局部图解决一个具体问题：同一个“拿箱子”动作，为什么要经过这么多边界。箭头上的文字标出传递的对象，而不是仅列模块名称。

```mermaid
flowchart LR
    A["XR 采样\n手腕 Pose + 手指 keypoints"] -->|source timestamp| B["Teleop Mapper\n标定 + 双臂 IK + Dex3 重定向"]
    B -->|candidate target [43]| C["ROS2 ActionTarget43\n候选动作与来源 state sequence"]
    C -->|action timestamp| D["ActionCentricSynchronizer\n匹配 state + 3 cameras"]
    D -->|AlignedStep| E["EpisodeWriter\nMCAP / Parquet / MP4"]
    E -->|validated episode| F["LeRobot V3\ntrain / validation / test"]
    F -->|normalized [50,32]| G["Pi0Pytorch\nFAST branch + Flow branch"]
    G -->|new action chunk| H["Async policy + RTC\n丢弃已过期前缀"]
    H -->|approved target [28]| I["Safety Gate\n限位 / 急停 / freshness"]
    I -->|published command| J["G1 actuators"]
```

> 这张图中 `ActionTarget43` 是采集链的时间锚点，`AlignedStep` 是训练样本的边界，Safety Gate 是模型输出和真实执行器之间的最后一道权限边界。

## 三类代码边界

### 机器人特定层 `src/g1_pi07/`

这里的代码不应该知道 Transformer 的隐藏维度。`joints.py` 只定义关节顺序和 43→28→32 的映射；`teleop/` 处理 XR 标定、双臂 IK 和手指重定向；`data/` 处理时间戳、样本记录、动作块和归一化；`deployment/` 维护动作缓存。它们共同回答“机器人数据是什么”。

### OpenPI 扩展层 `src/openpi/`

`models_pytorch/pi0_pytorch.py` 保持 π₀.₅ 的视觉语言前缀和连续动作专家，同时增加 FAST loss、subtask 生成、RTC 训练前缀以及动作 mask。`policies/unitree_g1_policy.py` 把 G1 的字段映射到 OpenPI 的标准输入；`training/g1_training.py` 把 episode-tail mask、sidecar 元数据和联合训练的梯度规则接到数据管线。

### ROS2 和部署层

`ros2_ws/` 只负责消息、节点和启动；`examples/unitree_g1/` 负责离线评估、RTC 回放和客户端。这个分层很重要：没有 ROS2 的单元测试仍能验证关节映射、时间对齐和滚动控制器；没有 GPU 的环境也能检查数据契约。

## 例子：箱子任务经过哪些表示

假设 XR 在时间戳 12.000 s 采到左手腕向前移动、右手腕保持高度、两只手指逐渐闭合。遥操作映射器先输出一个完整 43 维候选目标，但腿和腰没有被策略改写；记录器以这条候选动作的时间戳去找最近的机器人状态和三路相机；转换器把它存成一行训练样本；数据加载器从该时刻开始取未来最多 50 个动作。

模型看到的不是“一个 ROS2 消息”，而是三张 224×224 RGB 图像、语言指令、离散化 proprioception 和 `[50,32]` 的动作块。部署时模型返回的仍不是 43 维命令：只有前 28 维会恢复成双臂和双手目标，腿与腰由当前安全状态保留。

## 项目明确没有实现什么

源码 README 对实验性范围做了限制，这些限制必须进入文章结论：

- sidecar 可以携带成功、失败、干预和 advantage 元数据，但没有实现完整的 actor-critic 在线强化学习循环。
- MEM 字段可以追加到 prompt，但不是完整的持久化记忆系统。
- FAST 分支和 Knowledge Insulation 是实验性组合，不能直接称为官方 π₀.₇ 训练方法。
- ROS2、MoveIt2、Unitree SDK2、G1/Dex3 描述文件和模型权重不随仓库自动安装。

这不是削弱项目价值，而是把可复现范围说清楚：读者可以复现数据到模型到部署的代码骨架，但不能从仓库本身推导出官方模型权重或官方训练数据。

## 小结

这个项目最值得学习的不是把一个模型类改名，而是把“模型研究代码”和“机器人运行系统”接成了一条可审计链路。它通过固定维度、固定关节序、带符号的时间差、有效性 mask 和安全门，把原本容易靠经验拼接的系统变成了一组明确的接口。

**下一章聚焦**：这些接口首先从动作向量开始。第 2 章会逐项拆解 43 DoF 完整状态、28 DoF 策略空间和 32 DoF 模型空间的关系，并说明为什么 padding 维度必须同时出现在张量和 mask 中。
