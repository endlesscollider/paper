## 1. 配置树的分层原则

verl-vla 的 Hydra 配置严格遵循"谁消费、谁拥有"的组织原则——第 02 章讲过 `TrainCluster` 只是把配置树里对应的一段实例化成运行时对象，配置本身的层级结构直接映射运行时的所有权边界：

```text
workflow
├── cluster
│   ├── resource                     # 第02章：placement 描述，不含任何模型/算法参数
│   ├── actor_rollout_ref
│   │   ├── model                    # 第05章：checkpoint路径、adapter选择、LoRA开关
│   │   ├── actor                    # 第08章：SAC/SFT 训练超参
│   │   └── rollout                  # 推理相关（是否输出critic value等）
│   ├── env
│   │   ├── env_loop                 # 第03章：pipeline_stage_num、max_interactions
│   │   └── env_worker
│   │       ├── simulator             # 第07章：LIBERO/Arena/Piper 各自的环境配置
│   │       ├── teleop                 # 第07章：设备与遥操作策略选择
│   │       └── recorder               # 第07章：录制格式与开关
│   └── checkpoint                   # 恢复策略、保存频率上限
├── trainer                          # SAC/SFT trainer 的调度参数（rollout_interval等）
├── data                              # dataloader 配置
└── ray_kwargs                       # Ray 初始化和 runtime_env
```

记住这条规则就能快速定位"某个参数该改哪里"：**放置/资源问题改 `cluster.resource`，仿真器行为问题改 `cluster.env.env_worker.simulator`，算法超参改 `trainer`，模型选择改 `cluster.actor_rollout_ref.model`**。不要为了图省事把子配置的字段拍平塞进父配置里，路径本身就是文档。

## 2. 四种拓扑怎么选（复习第 02 章）

| 场景 | 该选的 cluster 配置 | 一句话判断依据 |
|---|---|---|
| 只想拿现成 LeRobot 数据集做纯监督训练 | `actor_cluster` | 不需要跟环境交互 |
| 只想跑遥操作/演示录制/回放验证 | `env_cluster` | 完全不需要模型 worker |
| 只想跑评估、自主数据采集、DAgger | `env_rollout_cluster` | 需要推理但不更新参数 |
| 在线交互式强化学习（SAC/PPO） | `env_actor_rollout_cluster` | 既要采数据又要更新参数 |

在 `env_actor_rollout_cluster` 内部，是否设置 `separate_rollout_model.enabled: true` 取决于硬件预算：

- **默认（colocate）**：GPU 少、显存紧张时的首选，代价是训练和推理严格串行。
- **分离部署**：有足够 GPU 分给独立的 rollout 资源池，希望用第 03 章讲的异步双缓冲流水线让训练和采集重叠、提升吞吐时使用。

## 3. 常用命令速查

**遥操作**（最小示例，来自 README）：

```bash
vvla-teleop \
  cluster.env.env_worker.simulator.libero.task_suite_name=libero_spatial \
  cluster.env.env_worker.simulator.libero.task_ids='[0]' \
  cluster.env.env_worker.teleop.devices='[keyboard]'
```

**覆盖资源拓扑**（第 02 章讲过的常见维度）：

```bash
python -m verl_vla.entrypoints.eval \
  cluster.resource.env.gpus_per_node=2 \
  cluster.resource.model.gpus_per_node=4 \
  cluster.env.env_worker.num_envs=8 \
  cluster.env.env_worker.simulator.simulator_type=libero
```

三个容易混淆的并行度参数，务必区分清楚：

| 参数 | 控制什么 |
|---|---|
| `cluster.resource.env.gpus_per_node` | env worker **进程数**（Ray worker 拓扑），影响资源调度 |
| `cluster.env.env_worker.num_envs` | 每个 env worker **内部**向量化的环境实例数，不额外占用 Ray worker |
| `cluster.env.env_loop.pipeline_stage_num` | 每个 env worker 内部起几条独立仿真子进程的流水线（第 03 章） |

增大 `num_envs` 不会申请更多 Ray 资源；增大 `resource.env.gpus_per_node` 才会改变分布式拓扑。混淆这两者是配置调优时最容易犯的错误。

## 4. Ray 运行环境变量

```yaml
ray_kwargs:
  ray_init:
    num_cpus: null
    logging_level: INFO
    runtime_env:
      env_vars:
        MUJOCO_GL: egl              # 无渲染GPU时用OSMesa/EGL做CPU渐染
        VERL_LOGGING_LEVEL: INFO
        HF_TOKEN: ${oc.env:HF_TOKEN,""}   # 敏感信息用环境变量插值,不写进配置文件
```

`HF_TOKEN` 这种敏感凭据永远通过 `${oc.env:VAR_NAME,默认值}` 从启动环境读取，不要直接写进版本控制里的 YAML——这是配置管理的基本卫生要求，空字符串默认值保证没有配置这个变量时配置本身仍能被正常解析（不会因为找不到某个 Hub token 而直接报错，除非真的需要访问受限模型）。

## 5. 新增一个组件时的检查清单

结合前面九章的内容，新增任意一类组件都遵循同一套流程：

**新增一个模型**（对照第 05 章）：
1. 在 `models/<name>/` 下用原生包加载策略，不复制模型代码
2. 写一个继承 `TrainableVLAModelBase` 的 wrapper，按需混入 `SupportSFTTraining`/`SupportSACTraining`
3. 在 `build_vla_model` 加一个显式分支
4. 在 `workflows/config/model/adapter/` 加对应 YAML
5. 确认 `export_policy` 能导出原生可加载的 checkpoint

**新增一个环境**（对照第 07 章）：
1. 定义 `env_type`，实现 `env_init`/`env_reset`/`env_step`/`env_close` 四个钩子
2. `env_step` 返回固定 schema 字典
3. 在 `workers/env/env_worker.py::init_worker` 加一个分支
4. 实现对应的 `BaseLeRobotStrategy`（`features()` + `make_frame()`）并注册
5. 如果需要遥操作，为每个 `(env_type, device_type)` 组合写一个 `InterventionStrategyBase` 实现并注册

**新增一个训练算法**：
1. 在 `trainer/<algo>/` 下实现 trainer 类，用 `TrainCluster` 的 `start/rollout/train/eval/save_checkpoint` 表达控制流（第 02 章的伪代码骨架）
2. 在 `workers/engine/<algo>/training_worker.py` 实现真正的 loss/更新逻辑
3. 在 `ACTOR_WORKER_REGISTRY`（第 04 章）注册对应的 Config 类和 Worker 类
4. 在 `workflows/train/<algo>.py` 写 workflow 组装逻辑
5. 加对应的 Hydra 配置组

## 6. 全系列回顾

| 章节 | 核心问题 |
|---|---|
| 01 全景图 | verl-vla 解决什么工程矛盾，三层架构分别负责什么 |
| 02 TrainCluster | 四种拓扑怎么落到具体资源池，八个核心 API 各自做什么 |
| 03 EnvLoop | pipeline stage 怎么让模型推理和环境仿真时间重叠 |
| 04 Worker 体系 | EnvManager 怎么隔离仿真器，Actor/Rollout 怎么共享或独立权重 |
| 05 模型集成契约 | 三个契约类怎么统一 ACT/Pi0.5/GR00T，backbone 只算一次的设计 |
| 06 Flow-SDE/DSRL | 流匹配策略怎么获得 log_prob，两条 SAC 化路线的对比 |
| 07 环境集成与人机协同 | BaseEnv 统一契约、动作块与实时接管、录制与遥操作三层分工 |
| 08 SAC 训练循环 | EpisodeBuffer、Bellman target、ReplayPool 双池采样、RLPD 混合采样 |
| 09 RECAP 工作流 | 六阶段自我提升闭环，Return/Advantage/Indicator 的精确计算 |
| 10 本章 | 配置速查与实战指南 |

如果只能记住三件事：**分层架构让同一套代码服务多种训练模式**（第 01-04 章）、**模型契约让训练算法和具体架构解耦**（第 05-06 章）、**环境契约让同一份数据链路服务训练/评估/人机协同**（第 07 章）。这三条设计原则贯穿 verl-vla 的每一处工程决策，也是理解任何"训练+环境+分布式"系统架构时值得借鉴的思路。
