# 第 02 章：配置继承链

> 前情提要：第 01 章划定了范围——本系列只讲 `miGenRL` 自己的链路，不涉及 `env.cfg_path` 指向的仿真环境配置怎么合并（那是另一套体系，属于 embodied-arena 环境侧，本系列不展开）。本章把 `miGenRL` 自己的三层 `base:` 继承规则和最终生效的配置值彻底摆开。

## 1. 为什么要读这一章

`stack_can_drawer_bimanual_base.yaml` 只有几十行，但它继承自：

```text
active_frame_phase_depth3_training.yaml   （Layer 0，最底层）
  ↑ base:
bimanual_activity_depth3_training.yaml     （Layer 1）
  ↑ base:
stack_can_drawer_bimanual_base.yaml        （Layer 2，最终配置，也是训练命令行里 --config 指定的那份）
```

真正生效的 `train.num_epochs` 是 240 还是 500？`data.camera_names` 有没有被 Layer 2 覆盖？如果不理解合并规则，答案只能靠猜。这一章给出一套可以机械执行的合并算法，以及三层合并后每一个关键字段的最终值。

## 2. `_deep_merge`：合并规则只有四条

`miGenRL` 训练配置的合并入口是 `load_config()`（`source/miGenRL/miGenRL/config/loader.py:92`），它递归地把每一层 base 加载进来再合并：

```python
def _load_config_recursive(config_path: Path, stack: tuple[Path, ...] = ()) -> dict[str, Any]:
    loaded = _load_yaml_mapping(config_path)
    base_refs = loaded.get("base") or loaded.get("train_base")
    if not base_refs:
        return loaded
    if isinstance(base_refs, (str, Path)):
        base_refs = [base_refs]

    merged: dict[str, Any] = {}
    for base_ref in base_refs:
        base_path = resolve_config_path(base_ref, relative_to=config_path.parent, include_base_dir=True)
        merged = _deep_merge(merged, _load_config_recursive(base_path, (*stack, config_path)))
    return _deep_merge(merged, loaded)
```

核心是最后一句：**先把所有 base 递归展开合并成 `merged`，再用当前层的内容 `loaded` 覆盖到 `merged` 上**。层次越靠"外面"（越靠近实验配置），优先级越高。

真正做覆盖的是 `_deep_merge`：

```python
def _deep_merge(base: dict[str, Any], override: dict[str, Any]) -> dict[str, Any]:
    merged = dict(base)
    for key, value in override.items():
        if isinstance(value, dict) and isinstance(merged.get(key), dict):
            merged[key] = _deep_merge(merged[key], value)   # 字典 → 递归合并
        else:
            merged[key] = value                              # 其他情况 → 直接覆盖
    return merged
```

拆开来只有四种情况：

| `override[key]` 的类型 | `base[key]` 的类型 | 结果 |
|---|---|---|
| 字典 | 字典 | 递归合并（两边的键取并集，同键按此表继续判定） |
| 字典 | 非字典或不存在 | 整个字典直接覆盖 |
| 列表 | 任意 | **整个列表直接覆盖**，不是拼接、不是去重合并 |
| 标量（字符串/数字/布尔/None） | 任意 | 直接覆盖 |

**最容易踩的坑是列表覆盖规则**。如果 Layer 0 定义了 `workflow.stages: [bc, rollout]`，Layer 2 只想加一个 `debug: true` 却不小心也重写了 `workflow.stages: [bc]`，结果就是 `rollout` 阶段整体消失——不会有任何报错提示，因为 YAML 语法完全合法，只是列表被整体替换了。本配置正是这样：Layer 2 显式写了 `workflow.stages: [bc]`，覆盖了 Layer 0 的 `[bc, rollout]`，这是第 01 章提到"训练和评估要分两条命令跑"的直接原因——不是框架不支持一条命令跑完，而是这份配置的作者主动选择了只声明 `bc` 阶段。

## 3. 三层合并逐字段推演

现在把三层配置真正摆在一起，看关键字段最终落在哪一层。

### 3.1 `data.qpos_keys`——完全被最外层覆盖

```yaml
# Layer 0 未定义 qpos_keys
# Layer 1:
data:
  qpos_keys:
    - geometry_obs/phase_index
    - geometry_obs/left_gripper_in_active_frame_positions
    - geometry_obs/left_gripper_in_active_frame_rot6d
    - geometry_obs/left_gripper_joint_positions
    - geometry_obs/right_gripper_in_active_frame_positions
    - geometry_obs/right_gripper_in_active_frame_rot6d
    - geometry_obs/right_gripper_joint_positions
# Layer 2:
data:
  qpos_keys:
    - geometry_obs/left_gripper_in_target_positions
    - geometry_obs/left_gripper_in_target_rot6d
    - geometry_obs/left_gripper_joint_positions
    - geometry_obs/right_gripper_in_target_positions
    - geometry_obs/right_gripper_in_target_rot6d
    - geometry_obs/right_gripper_joint_positions
```

按列表覆盖规则，**最终生效的是 Layer 2 的 6 个 key**（没有 `phase_index`，用的是 `in_target_` 而不是 `in_active_frame_`）。这不是偶然的用词差异——`in_active_frame` 对应 `geometry_active_frame` 表征，`in_target` 对应 `target_object_frame` 表征，这是两种不同的坐标系约定（第 03、04 章细讲）。Layer 2 同时把 `data.qpos_representation` 从 Layer 1 的 `geometry_active_frame` 改成了 `target_object_frame`，两处修改必须配套——如果只改了表征名字段却没改 qpos_keys 里的字符串，训练数据读取阶段会直接找不到对应的 HDF5 字段而报错。

### 3.2 `train.num_epochs` 与 `early_stopping`——数值型逐层收紧

| 字段 | Layer 0 | Layer 1 | Layer 2（最终） |
|---|---|---|---|
| `train.num_epochs` | 500 | 未覆盖 | **240** |
| `train.early_stopping.patience` | 30 | 未覆盖 | **40** |
| `train.keyframe_sample_prob` | 0.75 | 未覆盖 | **1.0** |
| `train.context_change_sample_prob` | 0.35 | 未覆盖 | **0.0** |

这一组修改是一致的：Layer 0 是一个通用的基线配置（500 epoch、75% 关键帧采样概率、35% 概率额外采样"参考系切换"帧），而 Layer 2 针对这个具体任务做了两处调整——一是把训练轮数从 500 砍到 240（配合更激进的 early stopping patience 40，说明这个任务收敛更快，不需要跑满 500 轮）；二是把 `keyframe_sample_prob` 提到 1.0、`context_change_sample_prob` 压到 0.0，即完全放弃均匀/上下文切换采样，只用关键帧采样。第 05 章会具体讲这个选择对训练效果的影响。

### 3.4 动作与观测维度是怎么推出来的

配置本身不直接写 `state_dim: 30`——这是从 `qpos_keys`/`action_keys` 列表和 `hand_synergy` 的隐变量维度间接推出来的。合并结果决定了原始维度：

| `qpos_keys` 项 | 原始宽度 | 经 hand_synergy PCA 后 |
|---|---|---|
| `left_gripper_in_target_positions` | 3 | 3 |
| `left_gripper_in_target_rot6d` | 6 | 6 |
| `left_gripper_joint_positions` | 22 | **6**（PCA 降维） |
| `right_gripper_in_target_positions` | 3 | 3 |
| `right_gripper_in_target_rot6d` | 6 | 6 |
| `right_gripper_joint_positions` | 22 | **6**（PCA 降维） |
| **合计** | 62 | **30** |

`action_keys` 走的是同一套逻辑，最终 `action_dim` 也是 30。这个数字会贯穿第 04、05、06 三章——它是网络输入输出的实际维度，但配置文件里从头到尾都没有出现"30"这个数字，它是合并结果 + hand_synergy 元数据共同决定的隐含值。这也是为什么改配置时最容易犯的错误是"改了 qpos_keys 但没意识到维度也变了，导致网络输入层维度不匹配"。

## 4. `env.cfg_path` 只是一个不透明指针

配置里还有一行：

```yaml
env:
  cfg_path: config/dexbench/humanoid/stack_can_into_drawer.yaml
```

第 01 章强调过：这一行对 `miGenRL` 来说是一个**不透明指针**——`miGenRL` 只需要知道"env 长什么样"最终会由这份文件决定，但它内部具体的场景搭建、机器人定义、任务判定，都不属于 `miGenRL` 的职责范围，本系列不会展开解析那份 YAML 内部的合并规则和内容结构。

`miGenRL` 真正关心的是这份 env 配置产出的仿真环境暴露出来的**观测和动作接口**——也就是第 03、04 章要讲的表征转换的输入输出两端。只要这个接口稳定（有哪些相机、动作是几维绝对位姿），`miGenRL` 侧的训练和推理逻辑就不需要关心环境内部怎么实现。这是一种接口隔离：即使后续把罐子换成别的物体、把任务步骤改掉，只要观测/动作接口的形状不变，`miGenRL` 这一侧的代码完全不需要改。

## 5. 小结与下一章

这一章确立了：

1. `miGenRL` 的 `_deep_merge` 只有四条规则，其中最容易踩坑的是**列表整体覆盖不合并**。
2. 三层继承推演出的最终配置里，`num_epochs=240`、`keyframe_sample_prob=1.0`、`workflow.stages=[bc]` 等关键行为参数全部来自最外层（Layer 2），验证了"离实验越近的层优先级越高"这条设计原则。
3. `action_dim=30`、`state_dim=30` 这两个贯穿全系列的数字，是 `qpos_keys`/`action_keys` 列表宽度之和减去 hand_synergy PCA 压缩掉的维度间接算出来的，配置文件里从未显式出现。
4. `env.cfg_path` 对 `miGenRL` 而言只是一个不透明指针，本系列只关心它暴露出来的观测/动作接口，不展开环境侧的实现。
