# Wan2.2 在机器人场景的适配：LoRA 微调与推理对齐

> Wan2.2 在通用视频上表现优秀，但直接用于机器人第一视角时几乎不可用。本章记录 Wan2.2 的 OOD 表现、VITRA ego4d 数据的 LoRA 微调、以及 fast-WAM 调用时遇到的四项推理差异排查。

## 前情提要

前三章我们完整拆解了 Wan2.2 的架构：3D Causal VAE + 30 层 DiT + Flow Matching。本章进入实际工程——当我们把这个模型拿来做机器人第一视角视频生成时，发生了什么。

---

## 1. 开发环境

整个 Wan2.2 的微调和推理基于 **diffsynth-studio** 框架开发。这是一个支持多种扩散模型的统一推理/训练框架，提供了：

- Wan2.2 的完整推理 pipeline（VAE 编解码 + DiT 去噪循环 + 采样器）
- LoRA 训练的封装
- 多种采样器实现（UniPC、DPM-Solver、Euler 等）

## 2. Wan2.2 原生推理：机器人场景的 OOD 表现

### 2.1 测试设置

- 模型：Wan2.2-TI2V-5B（原始参数，未经微调）
- 推理精度：bf16
- 测试了三种配置：20 Steps / 50 Steps / 20 Steps 无负向提示词

### 2.2 通用视频 vs 机器人第一视角

| 场景 | 效果 |
|------|------|
| 通用视频（动漫角色行走等） | **效果正常**，运动连贯、画质清晰 |
| 机器人第一视角 + 有负向提示词 | **严重不合理**，生成完全不像机器人操控场景 |
| 机器人第一视角 + 无负向提示词 | **相对合理但不稳定**，偶尔能看到合理的手部运动 |

测试用的 prompt 示例：`"Hold the transparent bowl over the sink."`

### 2.3 为什么 Wan2.2 在机器人场景是 OOD？

Wan2.2 的训练数据来自互联网视频——绝大多数是电影、动漫、自然风景、人物活动。几乎不包含：
- 机械手/灵巧手的第一视角操控视频
- 固定相机角度下的桌面操作
- 仿真环境的渲染画面

因此，当 prompt 描述机器人操作任务时，模型没有足够的先验来理解"第一视角看到的手应该怎么动"。

### 2.4 负向提示词为什么反而有害？

在通用场景中，负向提示词（如"低质量, 模糊, 变形"）通过 CFG 引导模型远离低质量区域。但在机器人场景中：

- 机器人仿真画面本身就"低分辨率、简单纹理"——这些特征和"低质量"的负向引导方向重叠
- CFG 把模型推离"简单场景"的同时，也推离了"机器人操控"的正确分布
- 结论：**在 OOD 场景下不应使用 CFG 的负向引导**

## 3. LoRA 微调：让 Wan2.2 认识机器人场景

### 3.1 微调数据

使用 **VITRA 数据集中 ego4d_cooking_and_cleaning** 的全部数据：

| 属性 | 值 |
|------|-----|
| 视频片段数 | 91,000 clips |
| 平均帧数 | 20.6 frames |
| 中位帧数 | 17 frames |
| 内容 | 人类第一视角的厨房操作视频 |

为什么选这个数据？因为它是第一视角(ego)的手部操作视频——和机器人第一视角操控在视觉特征上最接近。

### 3.2 LoRA 训练配置

| 参数 | 值 |
|------|-----|
| LoRA rank | 128 |
| 训练精度 | bf16 混合精度 |
| 等效 batch size | 2/GPU (accumulation_step=2) |
| GPU | 单卡 → 8 卡 |
| 训练步数 | 1000 / 2500 steps（单卡）→ 11k steps（8 卡 1 epoch）|

### 3.3 微调效果

单卡训练不同步数后的对比（测试 prompt: "Hold the transparent bowl over the sink", 21 frames, 20 Steps）：

| 配置 | 效果描述 |
|------|---------|
| 原始参数（未微调）| 几乎不可用，生成的画面和第一视角操控完全无关 |
| 单卡 1000 steps | 开始出现第一视角厨房场景，但手部动作不连贯 |
| 单卡 2500 steps | 场景更合理，手部开始有操控动作的趋势 |
| 8 卡 1 epoch (11k steps) | 能生成较合理的第一视角操控视频，但细节仍有失真 |

结论：**LoRA 微调能让 Wan2.2 "学会"第一视角操控场景的视觉分布**，但物理动态的理解仍然不足（手可能穿模、物体可能消失）。

## 4. 推理对齐：fast-WAM 调用 Wan2.2 的四项差异

### 4.1 先解释两个"推理框架"是什么

做实验时有**两套代码**都在调用同一个 Wan2.2 模型：

| 框架 | 是什么 | 谁写的 | 用途 |
|------|--------|--------|------|
| **diffsynth-studio** | 一个通用的扩散模型推理/训练库 | 开源社区 | LoRA 微调 Wan2.2、独立测试视频生成效果 |
| **fast-WAM 框架** | fast-WAM 项目自己的推理代码 | 本项目组 | 在 fast-WAM 的 MoT 架构中调用 Wan2.2 的 Video DiT 做联合推理 |

两套代码加载的是**同一个模型 checkpoint**（同一套权重），但因为推理流程的实现细节不同，生成结果**竟然不一致**。这很危险——如果你在 diffsynth 中测试效果不错，但 fast-WAM 实际推理时效果不同，就说明某个环节有 bug。

### 4.2 问题现象

同一个微调后的 checkpoint，在两个框架中生成的视频**画面完全不同**。必须排查原因。

### 4.3 差异排查：四个环节逐一对比

通过把两个框架的代码逐行对齐，定位了以下差异：

| 差异项 | diffsynth 做了什么 | fast-WAM 做了什么 | 为什么有影响 |
|--------|-------------------|------------------|-------------|
| **图像 crop** | 对首帧图像做 **center crop**（把长方形图裁成正方形） | **直接 resize**（不裁剪，拉伸到目标尺寸） | 首帧内容不同了——crop 后丢失了画面边缘的物体；resize 保留了全部内容但比例可能变形。DiT 从首帧 latent 出发去噪，首帧不同 → 整个视频完全不同 |
| **Text prompt 格式** | 直接把任务描述文字（如 "Hold the bowl"）送入 T5 编码器 | 可能在前面加了一段**模板前缀**（如 "A video of a robot..."）再拼上任务描述 | T5 编码出来的 token 序列不同 → Cross-Attention 给 DiT 的条件信号不同 → 生成结果不同 |
| **采样器 (sampler)** | 使用 **UniPC**（一种高阶 ODE 求解器） | 使用 **Euler**（最简单的一阶积分） | 采样器决定了"从噪声走到干净数据的路径"。同样 20 步，UniPC 走的是精心优化的曲线，Euler 走的是直线近似——到达的终点（最终视频）不同 |
| **推理精度** | bf16 | bf16 | 无差异（确认过了） |

### 4.4 什么是 center crop？为什么影响这么大？

**Center crop** 是图像预处理中的一种操作：从图像正中心裁出一个正方形区域，丢弃四周的像素。

```
原始图像 (832×480):
┌──────────────────────────────────┐
│  左边缘   │    中心区域    │  右边缘  │
│  (被丢弃)  │   (被保留)    │  (被丢弃) │
└──────────────────────────────────┘

Center crop 后 (480×480):
         ┌──────────────────┐
         │    中心区域       │
         │   (被保留)        │
         └──────────────────┘
```

对于机器人第一视角画面来说，被裁掉的边缘区域可能包含**待操控物体**或**桌面边界**——裁掉后模型看到的场景就不完整了。这就是为什么一个 crop 操作就能导致生成结果完全不同。

### 4.5 什么是采样器？为什么选择不同会影响结果？

回忆第 3 章：Flow Matching 推理时需要从 $x_1$（噪声）积分到 $x_0$（干净数据），走 N 步。每一步怎么走，就是采样器决定的：

| 采样器 | 原理 | 效果 |
|--------|------|------|
| **Euler** | 每一步直接按当前预测的 velocity 走一小段直线 | 简单但精度低，20 步时可能有明显误差 |
| **DPM-Solver** | 用 2 阶或 3 阶预测来估计更准的路径 | 同样步数下比 Euler 精确 |
| **UniPC** | 统一的预测-校正框架，结合多阶信息 | 通常是最优的——Wan2.2 官方推荐 |

类比：从 A 点走到 B 点，地图上有雾（你看不清远处）：
- Euler = 每走一步就按当前方向走直线（可能走偏）
- UniPC = 每走一步先预估前方路况，再校正方向（更准）

20 步的 Euler 和 20 步的 UniPC 最终到达的"B 点"（生成的视频）会有明显差异。

### 4.6 逐步对齐效果

按顺序一个一个修正 fast-WAM 框架中的差异，观察结果变化：

1. **去掉图像 crop**（改为直接 resize）→ 画面整体构图对齐了
2. **+ 调整 text prompt 格式**（去掉多余前缀）→ 文本语义对齐了
3. **+ 更换为相同采样器 (UniPC)** → 生成细节质量对齐了

三步修正后，两个框架的推理结果基本一致。

### 4.7 工程启示

这个排查过程的教训：

> 视频扩散模型对推理 pipeline 中**任何一个细节**的改变都极其敏感。一个 crop、一个 prompt 前缀、一个采样器选择——每一项单独就能让输出完全不同。

在将模型迁移到新框架时，**必须逐一验证每一步预处理和后处理是否一致**——不能只对齐模型权重就认为"迁移完成了"。

## 5. 进一步验证：Wan2.2 在不同分辨率下的表现

在第 9 章（瓶颈诊断）中会详细展开，这里先给出关键结论：

| 分辨率 | 帧数 | 效果 |
|--------|------|------|
| 1280×704 | 121f | ✓ 效果好（训练分辨率） |
| 1280×704 | 93f | ✓ 效果好 |
| 1280×704 | 9f | ✓ 基本正常 |
| 960×960 | 93f | ○ 可以接受 |
| **640×352** | 93f | **✗ 严重劣化** |

**即使在最佳分辨率（1280×704）下**，Wan2.2 在 EgoVLA 的仿真数据上仍然难以产生有意义的机器人操控视频——进一步证实了 OOD 问题不仅是分辨率导致的，更是**数据分布本质上的差异**。

---

## 6. 本章小结

| 发现 | 对后续实验的影响 |
|------|----------------|
| Wan2.2 对机器人场景完全 OOD | fast-WAM 的视频分支需要大量领域内数据才能产生有效的物理先验 |
| LoRA 微调能适配视觉分布 | 但物理动态理解仍不足——视频中手部/物体会失真 |
| 推理差异来自 crop/prompt/sampler | 工程上必须严格对齐推理环境 |
| 分辨率敏感性 | fast-WAM 的输入分辨率选择受限于 Wan2.2 的训练分布 |
