# 项目全貌：任务、数据集与仓库结构

> 前情提要：[Q-Chunking 论文精读](/论文综述/071_QChunking_RL与动作分块) 讲清楚了"为什么动作分块能解决 TD 学习偏差"这个数学问题。这一章开始转向工程视角——这个项目实际跑在什么任务上、数据从哪来、代码仓库怎么分工。读完这一章，你应该能回答"如果我想在自己的电脑上跑一遍这个项目，需要准备什么"这个问题。

## 一、这个项目在解决什么具体问题

论文的抽象问题是"offline-to-online RL 中怎么又快又稳地探索"，但代码层面这个问题被落实成一个具体、可衡量的任务设定：**给一个机器人操作任务，先给它一批离线演示数据（可能是次优的、不完整的），再让它上线跟环境交互一段时间，看它能不能快速把任务做好**。

用项目自己贯穿全文的例子说：`cube-triple` 任务里，一个机械臂要把 3 个方块依次搬到指定位置。离线数据集里的演示轨迹可能只搬对了 1-2 个方块,或者路径绕来绕去不够高效。目标是——用这批不完美的数据先预训练一下，再让机器人自己上线尝试,最终能稳定地把 3 个方块都搬对。

## 二、三大类任务环境，代码里怎么区分

`envs/env_utils.py` 里的 `make_env_and_datasets` 函数是所有任务的统一入口，靠**环境名字符串里的关键词**分发到不同的加载逻辑：

```python
def make_env_and_datasets(env_name, frame_stack=None, action_clip_eps=1e-5):
    if 'singletask' in env_name:
        # OGBench：论文主要实验用的环境
        env, train_dataset, val_dataset = ogbench.make_env_and_datasets(env_name)
        ...
    elif 'antmaze' in env_name and (...):
        # D4RL AntMaze
        from envs import d4rl_utils
        ...
    elif 'pen' in env_name or 'hammer' in env_name or ...:
        # D4RL Adroit（灵巧手操作）
        ...
    elif env_name.startswith("lift") or env_name.startswith("can") or ...:
        # RoboMimic：机械臂抓取/操作任务
        from envs import robomimic_utils
        ...
```

三类环境对应三种完全不同的数据来源和物理仿真器，先分别搞清楚它们是什么：

### 2.1 OGBench —— 论文的主战场

论文里反复出现的 `cube-triple`、`cube-quadruple`、`scene-sparse`、`puzzle-3x3-sparse` 全部来自 [OGBench](https://github.com/seohongpark/ogbench)（Offline Goal-conditioned RL Benchmark）,一个专门为离线目标条件 RL 设计的基准套件。这些环境名字里都带 `singletask` 关键词（比如 `cube-triple-play-singletask-task2-v0`）,通过 `ogbench.make_env_and_datasets(env_name)` 直接拿到环境和对应的离线数据集——数据集会自动从远程下载到 `~/.ogbench/data`，不需要手动准备。

`cube-quadruple`（4 个方块）用的是一个特别大的数据集（1 亿条 transition），README 专门给了单独的下载方式：

```bash
wget -r -np -nH --cut-dirs=2 -A "*.npz" https://rail.eecs.berkeley.edu/datasets/ogbench/cube-quadruple-play-100m-v0/
```

这解释了为什么 `main.py` 里有一整套 `dataset_replace_interval`、`ogbench_dataset_dir`、`dataset_idx` 相关的逻辑——当数据集大到不能一次性塞进内存时,代码要支持"训练过程中定期切换加载不同的数据分片文件"。

### 2.2 RoboMimic —— 人类遥操作数据

`lift`、`can`、`square` 这几个任务名字来自 [RoboMimic](https://robomimic.github.io/)，数据来自真人遥操作机械臂完成抓取/装配任务时录制的轨迹（下载链接指向 Multi-Human 版本的数据集）。这类环境需要先手动下载 `.hdf5` 数据文件放到 `~/.robomimic/{task}/mh/low_dim_v15.hdf5`,再用 `envs/robomimic_utils.py` 里的 `get_dataset` 函数解析：

```python
def get_dataset(env, env_name):
    rm_dataset = h5py.File(dataset_path, "r")
    demos = list(rm_dataset["data"].keys())  # 每个 demo 是一条完整的人类操作轨迹
    for ep in demos:
        a = np.array(rm_dataset[f"data/{ep}/actions"])
        obs = np.concatenate([np.array(rm_dataset[f"data/{ep}/obs/{k}"]) for k in low_dim_keys], axis=-1)
        ...
```

**这里有一个值得注意的工程细节**：RoboMimic 原始的观测是字典形式（`robot0_eef_pos`、`robot0_eef_quat`、`robot0_gripper_qpos`、`object` 四个独立的字段），代码把它们**拼接成一个扁平向量**（`np.concatenate(obs, axis=-1)`）,这样后续的 MLP 网络才能直接吃一个固定维度的输入,不需要单独处理字典结构。这是低维（low-dim，非图像）观测任务常见的做法。

### 2.3 D4RL —— AntMaze 与 Adroit

`antmaze`（蚂蚁机器人走迷宫）和 `pen`/`hammer`/`door`/`relocate`（Adroit 灵巧手系列任务）来自更早的 [D4RL](https://github.com/Farama-Foundation/D4RL) 基准。`envs/d4rl_utils.py` 里的 `get_dataset` 函数有一段专门处理 AntMaze 奖励的逻辑：

```python
if 'antmaze' in env_name:
    ...
    rewards = rewards - 1.0   # 把奖励整体减 1
```

**为什么要减 1**：D4RL 的 AntMaze 原始奖励是"到达目标给 1，否则给 0"，减 1 之后变成"到达目标给 0，否则给 -1"——这是把一个稀疏正奖励任务转换成了 [Q-Chunking 论文精读第 6.1 节](/论文综述/071_QChunking_RL与动作分块#6.1-主要对比) 提到的那种"惩罚式稀疏奖励"格式（每步 -1，直到成功变成 0），和 OGBench 里稀疏奖励的记法风格保持一致，方便统一处理折扣回报的数值范围。

## 三、数据集里到底存了什么：字段与格式

不管来自哪个环境，最终都会被统一包装成 `utils/datasets.py` 里定义的 `Dataset` 类，核心字段：

| 字段 | 含义 | 形状 |
|------|------|------|
| `observations` | 每个时间步的观测（状态向量或图像） | `(N, obs_dim)` |
| `actions` | 每个时间步执行的动作 | `(N, action_dim)` |
| `next_observations` | 执行动作后到达的下一个观测 | `(N, obs_dim)` |
| `rewards` | 即时奖励 | `(N,)` |
| `terminals` | 是否是轨迹的最后一步 | `(N,)`，0/1 |
| `masks` | 是否应该 bootstrap 下一状态的价值 | `(N,)`，`1 - terminals` |

这里必须区分原始专家演示和代码最终接收的数据：**专家演示通常只有状态和动作，BC 不需要 reward；但官方 QC 的 `critic_loss` 必须使用 reward。** 因此，进入 `Dataset` 前要由基准环境或任务规则计算/重标 reward。若始终没有 reward，只能先训练 BC-flow，不能执行离线 Critic 的 TD 更新。

`N` 是数据集里全部时间步的总数（所有轨迹拼在一起，不是轨迹数）。`envs/ogbench_utils.py` 里 `load_dataset` 函数的注释画了一张很清楚的示意图,说明"拼起来"具体是怎么拼的：

```
'observations': [s0, s1, s2, s3, s0, s1, s2, s3, ...]   # 轨迹 1 的 4 步，接着轨迹 2 的 4 步...
'actions'     : [a0, a1, a2, a3, a0, a1, a2, a3, ...]
'next_observations': [s1, s2, s3, s4, s1, s2, s3, s4, ...]
'terminals'   : [ 0,  0,  0,  1,  0,  0,  0,  1, ...]
```

**为什么这个格式很重要**：[第 3 章](./03_QC_从演示数据到在线策略的整体流程与优化目标) 会讲到，训练时要从这个"拍平"的大数组里，取"从某个位置开始连续 $h$ 步"的一整段动作块。因为 `terminals` 标记了每条轨迹的边界，采样函数才能正确判断"这一段有没有跨越到下一条轨迹"，避免把两条不相关的轨迹拼成一个动作块。

## 四、`Dataset` 类：内存里数据集的最小实现

`utils/datasets.py` 里的 `Dataset` 是一个继承自 `FrozenDict`（不可修改字典）的类，核心是把 numpy 数组包装起来，提供两个关键的采样方法：

```python
class Dataset(FrozenDict):
    def sample(self, batch_size, idxs=None):
        """随机采样一批单步 transition"""
        idxs = self.get_random_idxs(batch_size)
        return self.get_subset(idxs)

    def sample_sequence(self, batch_size, sequence_length, discount):
        """随机采样一批连续 h 步的动作块序列（训练分块 Critic/Actor 用）"""
        ...
```

`sample` 是最基础的单步采样（用于取一个 example batch 来初始化网络结构），`sample_sequence` 才是真正训练时用的。第 3 章会说明它怎样把单步轨迹加工成分块训练样本。这里先记住一个关键设计：**`Dataset` 是只读的，一旦创建就不会被修改**（`freeze=True` 时会用 `arr.setflags(write=False)` 把底层数组设成不可写）。这是因为离线阶段的数据集应该保持稳定，任何"新增数据"的需求都应该走另一个类——`ReplayBuffer`（继承自 `Dataset`，加上了 `add_transition` 方法），专门给在线阶段用（第 7 章细讲）。

## 五、仓库目录结构与职责划分

把这一章看到的所有模块串起来，整个仓库的分工是：

```
qc/
├── main.py                # QC / QC-FQL 训练入口：offline 预训练 + online 微调两阶段
├── main_online.py          # RLPD-AC / QC-RLPD 训练入口：只有 online 阶段（无独立离线预训练）
├── evaluation.py           # evaluate() 函数：跑固定局数的评测并统计成功率等指标
├── log_utils.py            # CsvLogger、wandb 相关的日志工具
├── agents/
│   ├── acfql.py            # ACFQLAgent：QC 和 QC-FQL 的具体实现（第 5 章）
│   ├── acrlpd.py           # ACRLPDAgent：RLPD-AC 和 QC-RLPD 的具体实现（第 6 章）
│   └── model.py            # 底层网络工具函数（初始化方式等）
├── envs/
│   ├── env_utils.py         # 统一环境入口 make_env_and_datasets，本章重点
│   ├── ogbench_utils.py     # OGBench 环境和数据集加载
│   ├── robomimic_utils.py   # RoboMimic 环境和数据集加载
│   └── d4rl_utils.py        # D4RL（AntMaze/Adroit）环境和数据集加载
├── utils/
│   ├── datasets.py          # Dataset / ReplayBuffer，本章重点，第 3、7 章会继续用到
│   ├── networks.py          # ActorVectorField（flow 网络）、Value（Critic）（第 2 章）
│   ├── encoders.py          # ImpalaEncoder（图像任务用的视觉编码器）（第 2 章）
│   └── flax_utils.py        # TrainState、ModuleDict —— JAX/Flax 参数管理封装（第 2、5 章）
├── rlpd_distributions/       # TanhNormal 等分布定义，RLPD 路线专用（第 6 章）
└── rlpd_networks/            # Ensemble、StateActionValue 等网络组件，RLPD 路线专用（第 6 章）
```

**这一章要传达的核心认知**：这个项目不是一个只能跑某一个特定任务的脚本，而是一套**统一的训练框架**，靠环境名字符串路由到三套不同的数据加载逻辑（OGBench/RoboMimic/D4RL），底层的 Agent 代码（`ACFQLAgent`/`ACRLPDAgent`）完全不关心数据来自哪里——只要数据被包装成统一的 `Dataset` 格式（`observations`/`actions`/`rewards`/`terminals`/`masks`），后续的训练逻辑就是一致的。这也是为什么第 3 至 5 章讲训练流程与算法实现时，不需要再区分数据来自 OGBench 还是 RoboMimic：数据加载层已经把差异抹平了。

## 六、下一章要解决的问题

这一章搞清楚了"数据从哪来、长什么样"。下一章会往前走一步——搞清楚接收这些数据的网络架构长什么样：`ActorVectorField` 这个 flow matching 网络具体是什么结构、`Value`（Critic）网络怎么做 ensemble、图像观测（如果有）怎么先过编码器再拼接到状态向量里。这些网络结构是第 3、4 章流程说明和第 5、6 章代码实现的直接基础。
