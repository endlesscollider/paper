## 1. 指标前缀的三层改写

同一个指标在 TensorBoard 里的名字经过三层加工，读日志时要能反推。

**第一层：worker 内部的键名。** `update_one_epoch` 产出的是 `sac/*`、`critic/*`、`actor/*`、`chunk_sac/*` 四类。

**第二层：ConRFT 的前缀改写。** `process_train_metrics` 被覆写：

```python
def _conrft_metric_key(key: str) -> str:
    if key.startswith("chunk_sac/"):
        return f"conrft/{key.removeprefix('chunk_sac/')}"
    if key.startswith("sac/"):
        return f"conrft/{key.removeprefix('sac/')}"
    return key

def process_train_metrics(self, metrics):
    metrics = super().process_train_metrics(metrics)
    return {_conrft_metric_key(key): value for key, value in metrics.items()}
```

所以：

| worker 内部 | 改写后 |
|-------------|--------|
| `sac/bc_loss` | `conrft/bc_loss` |
| `sac/critic_loss` | `conrft/critic_loss` |
| `chunk_sac/pending_action_slots_global` | `conrft/pending_action_slots_global` |
| `critic/q_mean` | `critic/q_mean`（**不改写**） |
| `actor/grad_norm` | `actor/grad_norm`（**不改写**） |
| `conrft/cql_loss` | `conrft/cql_loss`（直接加的，不经改写） |

**只有 `sac/` 和 `chunk_sac/` 被改成 `conrft/`。** `critic/` 和 `actor/` 保持原样——这是一个不太一致的设计，找指标时容易漏。

**第三层：runner 的阶段前缀。**

| 阶段 | 前缀 | 代码 |
|------|------|------|
| 阶段一 | `offline/` | `metrics = {f"offline/{key}": value for key, value in metrics.items()}` |
| 阶段二训练 | `train/` | `{f"train/{k}": v for k, v in self._aggregate_numeric_metrics(actor_result).items()}` |
| 阶段二评测 | `eval/` | `{f"eval/{k}": v for k, v in eval_metrics.items()}` |
| 环境 | `env/` | `get_env_metrics()` |
| rollout | `rollout/` | `get_rollout_metrics()` |
| 计时 | `time/` | `self.timer.consume_durations()` |

**完整例子**：BC loss 在阶段一是 `offline/conrft/bc_loss`，在阶段二是 `train/conrft/bc_loss`。

## 2. 首先要看的六个指标

如果只能看六个，看这些。

### 2.1 `conrft/bc_loss`

**监控什么**：策略采样动作与演示动作的 masked MSE（第 05 章 6.1 节）。

| 阶段 | 期望值 | 期望形状 |
|------|--------|----------|
| 阶段一 | 约 $0.39$ 起，缓慢下降 | 单调但很平 |
| 阶段二 | 同量级 | 基本水平（expert 池固定） |

**实测参考**：warmup 第 35 次更新 `0.3903`。

**为什么不会降到很低**：策略是随机的，flow SDE 每步注入噪声（第 05 章 2.2 节算过标准差从 0.433 递减到 0.144）。即使 gate 完美，单次采样和演示动作之间仍有噪声偏差。$0.3903$ 对应逐坐标 RMS $\sqrt{0.390} = 0.625$，而动作归一化到 $[-1,1]$——所以当前主要由采样噪声支配。

**告警**：

| 观察 | 诊断 |
|------|------|
| **完全水平且无任何抖动** | BC 项没有梯度（第 01 章 9.14 的复发）。立刻看 `actor/action_grad_norm` |
| 掉到 $0.01$ 以下 | 采样退化（噪声消失）或过拟合到极少数样本 |
| 单调上升 | 三项博弈失衡，Q 项或 W2 项把策略拖离演示分布 |

### 2.2 `actor/action_grad_norm`

**监控什么**：`policy["actions"].grad` 的 L2 范数。这是"actor loss 的梯度真的到了动作上"的**直接证据**。

```python
if actor_output.policy_actions is None:
    action_grad_norms.append(0.0)
else:
    action_gradient = actor_output.policy_actions.grad.detach().float()
    action_grad_norms.append(action_gradient.norm().item())
    action_grad_maxes.append(action_gradient.abs().max().item())
```

**实测参考**：`0.0142`。

**告警**：**恒为 0 是最严重的信号**。它意味着 actor 的三项 loss 全都没有梯度，训练完全空转。这个指标存在的唯一目的就是抓这种情况——第 01 章 9.14 那个 bug 如果当时有人看这个指标，会在第一次跑阶段一时就发现。

配套看 `actor/action_grad_max`（最大绝对值）。如果 `norm` 正常但 `max` 特别大（比如超过 norm 的一半），说明梯度集中在极少数坐标上，可能有数值问题。

### 2.3 `critic/q_mean` 与 `critic/target_mean`

**监控什么**：critic 在数据动作上的输出均值，以及 TD target 的均值。

**期望范围**：$[0, 1]$。第 06 章 4.2 节推导过——`terminal_success` 奖励下，成功轨迹上 $Q \approx \gamma^{\text{剩余物理步}}$，失败轨迹上 $Q \approx 0$。

**期望形状**：阶段一前 100 次快速从随机初值收敛进 $[0,1]$，之后缓慢上升（因为价值信息从 episode 末尾往前传播，第 07 章 9 节）。

**告警**：

| 观察 | 诊断 | 处理 |
|------|------|------|
| 跑到负数 | Cal-QL 压过头 | 调小 `cql_alpha`；检查 `calql_positive_bound_fraction` 是否下滑 |
| 超过 1 并继续涨 | TD 发散 | 检查 `bootstrap_mask` 语义、`gamma`、twin-Q 是否真在取 min |
| `q_mean` 和 `target_mean` 差距很大且不收敛 | critic 追不上 target | 调小 `tau`（让 target 更慢）或调小 critic lr |
| 在 $[0,1]$ 内但和成功率不相关 | critic 学到"平均价值"而非"这个动作好不好" | 这是 chunk-SAC 的经典难题，ConRFT 没有专门机制处理 |

**一个进阶用法**：把 `q_mean` 按 `chunk_sac_is_expert` 分层看。如果 expert 样本的 $Q$ 明显高于在线样本，说明 critic 认为演示比策略好——这在训练早期是正常的，如果一直如此说明策略没进步。

### 2.4 `actor/flow_g_gate_deviation`

**监控什么**：$\mathbb{E}[|g - 1|]$，也就是 Flow-G gate 偏离恒等的平均幅度。

```python
flow_g_gate_deviations.append((flow_g_gate.float() - 1.0).abs().mean(dim=(1, 2)))
```

**这是"策略走了多远"的最直接读数。** gate 的取值范围是 $(0, 2)$，恒等点 1.0。

**实测参考**：warmup 第 35 次 `0.0221`（gate 在 $[0.978, 1.022]$ 附近）。

**期望形状**：从 0 开始（恒等初始化）单调上升，斜率随训练放缓。

**告警**：

| 观察 | 诊断 | 处理 |
|------|------|------|
| 恒为 0 | actor 完全没训 | 看 `conrft/actor_updated`；看 `actor/action_grad_norm` |
| 阶段二起点不是阶段一的终点值 | **resume 时 gate 被重置了** | 检查 `preserve_stage1_flow_g_adapter`（第 12 章 5 节）。日志里应该有 "Preserving the Stage-1 Flow-G adapter" |
| 急速上升超过 $0.2$ | Q 项在把策略拖走 | 调小 `q_weight_online` 或调大 `w2_weight` |
| 到达 $1.0$ 附近 | gate 已经饱和（$g \to 0$ 或 $g \to 2$） | 策略已经严重偏离，检查是否 critic 崩了 |

配套看 `actor/flow_g_gate_mean`（$\mathbb{E}[g]$）。它和 deviation 一起能区分两种情况：

- `mean ≈ 1` 但 `deviation` 大 → gate 在不同坐标上有正有负的偏移（正常的"精细调整"）
- `mean` 明显偏离 1 → gate 整体放大或缩小速度场（更激进的改变）

### 2.5 `conrft/cql_bound_rate` 与 `conrft/calql_positive_bound_fraction`

**只在阶段一有**（在线阶段不算 CQL）。

`cql_bound_rate` = 12 个候选里被 MC 下界抬升的比例：

```python
bound_rate = (candidates < bounds).float().mean()
```

| 观察 | 含义 | 处理 |
|------|------|------|
| 全程接近 0 | Q 值从没跌破下界，Cal-QL 等价于 CQL | `cql_alpha` 可能太小，或 $G_t$ 的量级不对 |
| 初期 0，后期升到 $0.2\sim0.6$ | **理想**：先正常压低，压到底线后自动止损 | 不用动 |
| 一开始就接近 1 | 下界过高或 $\alpha$ 太大导致一步压穿 | 调小 `cql_alpha` |
| 剧烈震荡 | Q 值在下界附近抖 | 调小 critic lr 或 `cql_alpha` |

`calql_positive_bound_fraction` = 这批样本里 $G_t > 0$ 的比例，也就是**来自成功 episode 的样本占比**（第 07 章 6 节）：

```python
positive_bound_fraction = (lower_bounds > 0).float().mean()
```

**当前有效 run 上是 `1.0`**——BC 数据集全部成功。

| 观察 | 含义 |
|------|------|
| $1.0$ | 全部样本有有效下界，Cal-QL 校准最强 |
| 下滑到 $0.7$ 以下 | 约 30% 的样本上 Cal-QL 退化成普通 CQL，那些样本的 $Q$ 可以被压到负数 |
| 接近 0 | Cal-QL 完全失效 |

**这是第 01 章 9.10 那条"转为监控"的问题的观测点。** 它下滑的唯一途径是 replay 里混入失败样本，在当前架构下不会自发发生（阶段一没有环境），但换数据集会。

### 2.6 `conrft/critic_loss` 与 `conrft/cql_loss`

`critic_loss` 是 TD 项 + CQL 项的总和（乘 `gradient_accumulation` 还原过）：

```python
critic_losses.append(critic_loss.item() * (1.0 if uses_distributed_normalizers else self.gradient_accumulation))
```

`cql_loss` 是保守项**本身**（未乘 `cql_alpha`）：

```python
self._conrft_critic_metrics.append({"cql_loss": cql_loss.detach().item(), ...})
```

**实测参考**：`critic loss = 0.0718`。第 08 章算过一个数值例：$\mathcal{R}_{\text{Cal}} = 0.028$，乘 $\alpha = 0.1$ 得 $0.0028$，占总 loss 约 4%。

**怎么用这两个数**：算出 CQL 项的实际份额

$$
\text{CQL 份额} = \frac{\alpha \times \texttt{cql\_loss}}{\texttt{critic\_loss}}
$$

| 份额 | 诊断 |
|------|------|
| $< 1\%$ | 保守项几乎不起作用，考虑调大 `cql_alpha` |
| $3\% \sim 20\%$ | 合理区间 |
| $> 50\%$ | 保守项主导，TD 学不动，调小 `cql_alpha` |

配套指标 `conrft/cql_diff`（= `q_diff.mean()`，也就是 $\mathcal{R}_{\text{Cal}}$ 本身）和 `conrft/cql_ood_q`（归一化后的软最大值）。

**`cql_diff` 长期接近 0 的两种可能**，要分清：

1. **好的情况**：critic 已经正确地把数据动作排在候选之上，保守项自动收手（第 08 章 3.3 节的自终止性质）。此时 `q_mean` 应该在 $[0,1]$ 内且稳定。
2. **坏的情况**：critic 对所有动作给出几乎相同的 $Q$ 值（表示塌缩），候选和数据动作区分不开。此时 `q_mean` 的**方差**会很小——需要额外看 `critic/td_abs_p50/p90/p99` 的分布。

## 3. TD 误差分位数

`critic/td_abs_p50` / `p90` / `p99` 是 $|Q - y|$ 的分位数。它们比 `critic_loss`（均方）更能反映分布形状。

**为什么要看分位数而不只看均值**：MSE 被大误差样本主导。如果 99% 的样本 TD 误差是 0.01、1% 是 1.0，MSE 会被那 1% 拉高，从均值看不出"绝大多数样本其实学得很好"。

**期望形状**：三条线都下降，且 `p99 / p50` 的比值收敛到一个稳定值（比如 5~20）。

**告警**：

| 观察 | 诊断 |
|------|------|
| `p50` 很小但 `p99` 很大且不降 | 有一小批"难样本"始终学不会。可能是 terminal 附近的样本（奖励突变） |
| 三条线几乎重合且都很小 | critic 输出趋于常数（表示塌缩）。配合 `q_mean` 方差确认 |
| `p99` 突然跳高 | replay 里进了新分布的数据（在线阶段正常，阶段一异常） |

## 4. 在线阶段特有的指标

### 4.1 采集量

| 指标 | 含义 |
|------|------|
| `conrft/online_valid_physical_steps_global` | 累计采集的有效物理步（全局） |
| `conrft/online_action_slots_global` | 累计的动作槽位数（含 padding） |
| `conrft/online_padded_action_slots_global` | 两者之差，也就是 padding 总量 |
| `conrft/online_valid_physical_steps_per_env` | 除以 `env.train.total_num_envs`（64） |

**padding 率** $= \texttt{padded} / \texttt{action\_slots}$ 是一个有用的派生量。它反映"平均 chunk 有多满"。

理论值：如果 episode 长度是 350、chunk 长 16，那么 $350 = 21\times16 + 14$，最后一个 chunk 只有 14 步有效，padding 率约 $2/(22\times16) = 0.57\%$。**如果实测远高于这个值，说明 episode 提前终止很多**（早期成功或早期失败）。

`online_valid_physical_steps_per_env` 是判断"采集是否在推进"的最直接指标。如果它不涨，说明环境卡住了。

### 4.2 pending 与丢弃

| 指标 | 含义 |
|------|------|
| `conrft/pending_action_slots_global` | 当前有多少动作槽位属于未完成的 episode |
| `conrft/pending_valid_physical_steps_global` | 同上，有效步版本 |
| `conrft/discarded_pending_action_slots_on_resume_global` | **累计**被丢弃的 pending 槽位 |
| `conrft/discarded_pending_valid_steps_on_resume_global` | 同上 |
| `conrft/discarded_physics_invalid_episodes_global` | 因物理异常被丢弃的 episode 数 |

`pending_*` 在异步在线模式下**恒不为零是正常的**（64 个环境总有在半途的）。它进这份手册是因为它曾经会让存 checkpoint 崩溃（第 01 章 9.13），现在 `require_empty_pending_on_save: false` 允许了。

`discarded_pending_*` 是**累加**的，每次 resume 会把当时的 pending 加进去（第 12 章 7.1 节）。所以它反映"历史总共丢了多少数据"。如果它相对 `online_valid_physical_steps_global` 占比很大（比如超过 10%），说明 resume 太频繁，浪费了很多采集。

`discarded_physics_invalid_episodes_global` 涨得快说明 Isaac Sim 的仿真在出问题（穿模、爆炸、NaN），要去看 env worker 的日志。

### 4.3 权重同步

日志里的（不是 TensorBoard 指标）：

```text
Weight sync coalesced N times.
Request total M times.
```

**$N/M$ 是关键比值**（第 10 章 5.4 节）：

| 比值 | 诊断 |
|------|------|
| 接近 0 | 同步很快完成，策略新鲜度符合配置意图 |
| $0.3 \sim 0.5$ | 同步偶尔跟不上，实际间隔比 50 秒长 |
| 接近 1 | **同步耗时超过 50 秒**，rollout 拿到的权重远比预期旧。调大间隔或检查 syncer |

另外 `train/replay_channel_qsize`（runner 加的）反映 `actor_channel` 的积压：

```python
training_metrics["train/replay_channel_qsize"] = self.actor_channel.qsize()
```

**持续增长说明 actor 消化不过来**——drain 限流是 256 条，如果 env 产出速度超过这个，队列会堆积。堆积本身不致命（数据没丢），但意味着 replay 里的数据越来越旧。

### 4.4 replay 统计

`conrft/replay_buffer/*` 来自 `self.replay_buffer.get_stats()`。具体键取决于 buffer 实现，但通常包含总样本数、expert 样本数、容量占用等。

**要盯的是 expert 计数是否变化**（第 11 章 2 节提过的疑点）：`expert_cache_size: 256` 限制了 expert 池的大小。如果这个数字从 resume 之后就固定不变，说明 BC 项在反复拟合同 256 个样本，有过拟合风险。这一点本系列没有核实到 buffer 的缓存管理层，**建议实测时确认**。

## 5. 在当前配置下失效的指标

这一节是这份手册最实用的部分——避免在没有信息量的曲线上浪费时间。

| 指标 | 为什么失效 | 恒定值 |
|------|-----------|--------|
| `conrft/path_log_pi` | `compute_path_log_prob: false`（第 05 章 2.3 节），`sample_chunk_sac_action` 不再累加转移 log 密度 | **0** |
| `conrft/normalized_path_log_pi` | 同上 | **0** |
| `conrft/path_entropy_estimate` | 由 `log_pi` 导出 | **0** |
| `conrft/normalized_path_entropy_estimate` | 同上 | **0** |
| `conrft/alpha` | `entropy_tuning.alpha_type: fixed_alpha` + `initial_alpha: 0.0` | **0** |
| `conrft/alpha_loss` | 没有 alpha optimizer | **0** 或不上报 |
| `conrft/reference_action_mse`（阶段一） | W2 项是零张量（第 09 章 4 节），`diagnostics["action_mse"]` 恒为 0 | **0** |
| `conrft/advantage` | `ConRFTActorObjective` 返回 `zeros` | **0** |
| `conrft/awr_weight_mean` / `awr_weight_max` | `actor_use_awr_weights: false`，objective 返回 `ones` | **1** |
| `conrft/awr_saturation_fraction` | 同上 | **0** |
| `conrft/data_q` | ConRFT 把它设成和 `actor_q` 相同（`data_q=policy_q.detach()`） | 与 `actor_q` 重复 |
| `conrft/critic_advantage_loss` / `critic_value_loss` | `flat_absolute` 架构不分解 $V/A$ | **0** |
| `conrft/critic_pair_*` | same-state ranking / TD 被强制禁用（第 04 章） | **0** |
| `critic/calibration_*` | `critic_calibration.enabled: false` | 不上报或恒定 |
| `conrft/reference_q1_advantage` / `q2_advantage` / `critic_disagreement` / `gate_fraction` | 这些是 `actor_reference` 通路的诊断，ConRFT 不用 | **0** |
| `conrft/flow_g_bc_warmup` | `_sac_flow_in_bc_warmup()` 恒等于"是否离线阶段"，在线恒 False、离线恒 True | 阶段内恒定 |
| `conrft/batch_expert_fraction`（阶段一） | 阶段一 replay 里全是 expert | **1.0** |

**一共 18 个指标是常数。** 这是"ConRFT 复用 Chunk-SAC 基类"的直接后果——基类为所有算法变体上报全套指标，ConRFT 只用其中一小部分。

**读日志的建议**：先按上表把这些过滤掉，剩下的才值得看。

## 6. 分阶段的检查清单

### 6.1 阶段一启动后 5 分钟内

| 检查 | 期望 | 失败意味着 |
|------|------|-----------|
| `offline/actor/action_grad_norm` | 非零 | actor 三项 loss 都没梯度 |
| `offline/conrft/bc_loss` | $0.3\sim0.5$ 量级 | 数据或归一化有问题 |
| `offline/critic/q_mean` | 正在向 $[0,1]$ 收敛 | critic 初始化或 TD target 有问题 |
| `offline/conrft/calql_positive_bound_fraction` | 期望值（当前数据集是 1.0） | MC 回报没算对 |
| `offline/conrft/cql_loss` | 非零 | 保守项没生效 |
| `offline/actor/flow_g_gate_deviation` | 从 0 开始上升 | actor 没训 |

### 6.2 阶段一 800 次结束时

| 检查 | 期望 |
|------|------|
| `critic/q_mean` | 稳定在 $[0,1]$ |
| `critic/td_abs_p50` | 明显低于起点 |
| `actor/flow_g_gate_deviation` | 一个非零的稳定值（记下来，阶段二要对比） |
| `conrft/cql_bound_rate` | 在 $0.2\sim0.6$ |
| checkpoint | 8 个 `complete_rank_*` 全在，`update_step = 800` |

### 6.3 阶段二启动后第一个 step

| 检查 | 期望 | 失败意味着 |
|------|------|-----------|
| 日志里有 "Preserving the Stage-1 Flow-G adapter" | 有 | resume 走错路径了（第 12 章 5 节） |
| `train/actor/flow_g_gate_deviation` | **等于阶段一结束时的值** | gate 被重置 |
| `train/critic/q_mean` | 和阶段一结束时同量级 | critic 没正确加载（第 12 章 6 节的 reshard 校验） |
| `train/conrft/actor_updated` | 1（或非零） | actor 没参与更新，检查 `update_step >= 800` |
| `train/conrft/reference_action_mse` | **非零**（W2 项在线阶段真算） | `return_bc_reference` 没生效 |
| `train/conrft/cql_loss` | **不存在或为 0** | 在线误开了 CQL |

**第二行是最重要的一条**：它是"阶段交接是否成功"的单点验证。gate deviation 是一个连续量，如果阶段二第一步的值和阶段一最后的值一致，说明 adapter 被完整保留了。

## 7. 一张速查表

按"我想知道 X"组织。

| 我想知道 | 看这个 |
|----------|--------|
| actor 到底在不在训 | `actor/action_grad_norm` 非零 + `actor/flow_g_gate_deviation` 上升 |
| 策略走了多远 | `actor/flow_g_gate_deviation`（速度场口径）+ `conrft/reference_action_mse`（动作口径） |
| critic 靠不靠谱 | `critic/q_mean` 在 $[0,1]$ + `critic/td_abs_p50` 下降 + `critic/td_abs_p99` 不失控 |
| 保守项有没有起作用 | $\alpha \times$ `conrft/cql_loss` / `conrft/critic_loss` 在 $3\%\sim20\%$ |
| Cal-QL 的校准强不强 | `conrft/calql_positive_bound_fraction` 接近 1 + `conrft/cql_bound_rate` 在 $0.2\sim0.6$ |
| 阶段交接成不成功 | 阶段二第一步的 `flow_g_gate_deviation` 等于阶段一最后的值 |
| 采集在不在推进 | `conrft/online_valid_physical_steps_per_env` 单调上升 |
| 数据新不新鲜 | 日志里 coalesced/request 比值 + `train/replay_channel_qsize` |
| 丢了多少数据 | `conrft/discarded_pending_*` 相对 `online_valid_physical_steps_global` 的占比 |
| 仿真有没有出问题 | `conrft/discarded_physics_invalid_episodes_global` |
| 方法有没有效 | `eval/*`（**只有这个能回答**，训练环境的 `env/*` 不能直接和 BC 基线比） |

**最后一行值得强调**：训练环境用随机 layout、且策略权重最多滞后 50 秒，它的成功率**不能**和 BC 基线在 48 个固定 layout 上的结果直接比较。判断方法有效性只能靠 `eval/*`。这就是第 01 章 9.1 为什么把"评测被关掉"列为 P0 的原因。

## 8. 小结

| 主题 | 关键结论 |
|------|----------|
| 前缀改写 | `sac/` 和 `chunk_sac/` → `conrft/`；`critic/` 和 `actor/` **不改** |
| 阶段前缀 | 阶段一 `offline/`，阶段二 `train/` 和 `eval/` |
| 最重要的六个 | `conrft/bc_loss`、`actor/action_grad_norm`、`critic/q_mean`、`actor/flow_g_gate_deviation`、`conrft/cql_bound_rate` + `calql_positive_bound_fraction`、`conrft/critic_loss` + `cql_loss` |
| 最强的单点信号 | `actor/action_grad_norm` 恒为 0 → 训练完全空转 |
| 阶段交接的验证 | 阶段二第一步的 `flow_g_gate_deviation` 必须等于阶段一最后的值 |
| Q 值范围 | $[0,1]$。超出说明 critic 坏了 |
| CQL 份额的算法 | $\alpha \times$ `cql_loss` / `critic_loss`，合理区间 $3\%\sim20\%$ |
| 失效指标 | **18 个**恒为常数（`log_pi` 系列、`alpha` 系列、AWR 系列、pair 系列、阶段一的 `reference_action_mse` 等） |
| 判断方法有效性 | **只能看 `eval/*`**，训练环境的成功率不可直接对比 |
