# 全景图：为什么机器人学习需要一个新的物理引擎

> 系列第 1 章。本章不涉及代码细节，目标是建立一个问题：现有的物理引擎（MuJoCo、PhysX/Isaac Gym、Bullet）已经很成熟了，为什么 NVIDIA、Google DeepMind、Disney Research 还要联手做一个新的 Newton？搞清楚这个问题，后面每一章讲的具体设计选择才有意义。

## 贯穿全文的例子

> **场景**：假设你要训练一个人形机器人的行走策略。你需要同时满足几个看起来互相冲突的要求：仿真速度要快（强化学习通常需要几十亿步交互），仿真要能在 GPU 上跑几千个并行环境（否则采样效率太低），机器人的手部要能操作柔软的绳缆和布料（不只是刚体），策略网络训练完之后最好还能用同一套仿真做基于梯度的轨迹优化（不只是黑盒强化学习），而且你的团队里有人喜欢用 URDF 描述机器人、有人已经把整套场景用 USD 搭好了。这个系列会反复回到"一个人形机器人的仿真训练管线"这个场景，看 Newton 具体怎么满足这些要求。

## 一、先看清楚问题：物理引擎不是一个,是很多个

### 1.1 机器人仿真领域已有的几条主流路线

在 Newton 出现之前，机器人学习和仿真研究里已经有几个成熟的选择，各自面向不同的取舍：

| 引擎 | 核心设计取向 | 典型代表场景 |
|------|-------------|-------------|
| **MuJoCo**（原生 CPU 版） | 精确、稳定的广义坐标铰接体动力学 | 机器人控制研究、经典 RL benchmark（如 dm_control） |
| **PhysX / Isaac Gym / Isaac Sim** | GPU 上跑上千并行环境，工业级渲染管线 | 大规模并行 RL 训练、Sim2Real 项目 |
| **Bullet** | 通用、跨平台，游戏和机器人都能用 | ROS 生态里最常见的默认仿真器之一 |
| **Brax / MJX**（MuJoCo 的 JAX 移植） | 完全用 JAX 写，天然可微、天然向量化 | 需要梯度的策略优化、meta-learning 研究 |
| **warp.sim**（NVIDIA Warp 内置模块） | GPU kernel 编写框架自带的仿真子模块 | Warp 用户快速搭建可微物理场景 |

这些引擎没有一个是"错的"，但每一个都在某个维度上做了取舍。MuJoCo CPU 版精确稳定，但天生是单线程 CPU 计算，扩展到几千个并行环境很吃力。PhysX/Isaac Gym 并行度极高，但物理模型的精度和 MuJoCo 比通常有差距，尤其在接触丰富（contact-rich）的操作任务上容易出现"仿真里能成功、真机上不行"的落差。Brax/MJX 可微性和并行性都好，但生态（导入 URDF/MJCF/USD、渐进式功能扩展、和现有工具链对接）不如前两者成熟。

**这就是 Newton 要解决的核心矛盾**：现有引擎里，"求解器精度"、"GPU 并行规模"、"可微性"、"格式生态兼容性"这四个维度，几乎没有一个引擎能同时在全部维度上做到不妥协——用户要么牺牲精度换并行度，要么牺牲可微性换生态成熟度。

### 1.2 Newton 的解法：不是发明新的物理算法，而是重新设计"引擎"这一层

Newton 团队做出的一个关键判断是：**物理求解算法本身（怎么解约束、怎么算接触力）已经有很多成熟且各有优势的实现了（MuJoCo 的求解器、XPBD、VBD 等），真正缺的是一个能把这些求解器统一接进同一套数据模型、同一套 GPU 并行框架、同一套可微计算图里的"引擎层"**。

这个判断直接决定了 Newton 的架构：它不是"发明一种新的物理算法去替代 MuJoCo"，而是把 MuJoCo Warp（DeepMind 维护的 MuJoCo GPU 移植版）作为**主力求解器之一**直接集成进来，同时并存另外五种求解器（XPBD、VBD、Featherstone、SemiImplicit、Kamino），让用户根据任务需求在同一套 API 之下自由切换。这也是为什么后面第 5 章要专门讲"六种求解器怎么选"——理解这个设计选择,才能理解 Newton 和"另起炉灶发明一个新物理引擎"的项目（比如早期一些从零写刚体动力学的实验性引擎）的本质区别。

## 二、Newton 的技术地基：NVIDIA Warp

### 2.1 为什么先讲 Warp

Newton 的官方定义是"一个建立在 [NVIDIA Warp](https://github.com/NVIDIA/warp) 之上的 GPU 加速物理仿真引擎"。理解 Warp 是什么，是理解 Newton 整套设计的前提——很多后面章节会遇到的技术选择（比如为什么 Newton 的所有核心数据都以扁平数组存储，而不是面向对象的树状结构）根源都在 Warp 这一层。

Warp 是 NVIDIA 开发的一个 Python 框架，核心能力是：**允许开发者用接近普通 Python 的语法写计算核（kernel），这些核会被 just-in-time 编译成高性能的 CUDA 代码（在 GPU 上跑）或 C++ 代码（在 CPU 上跑），并且天然支持自动微分**。换句话说，Warp 让开发者不需要直接手写 CUDA C++，就能获得接近手写 CUDA 的性能，同时保留 Python 的开发效率。

```python
import warp as wp

@wp.kernel
def integrate_bodies(
    body_q: wp.array(dtype=wp.transform),
    body_qd: wp.array(dtype=wp.spatial_vector),
    dt: float,
):
    # tid() 返回当前 GPU 线程处理的索引——每个刚体由一个独立线程处理
    tid = wp.tid()
    # 用当前刚体的速度对其位姿做一步简单的显式积分
    body_q[tid] = wp.transform_integrate(body_q[tid], body_qd[tid], dt)
```

上面这段伪代码展示了 Warp kernel 的基本形态：`wp.tid()` 拿到当前 GPU 线程编号，函数体描述"这一个线程该做什么"，Warp 负责把这个逻辑铺开到成千上万个 GPU 线程上并行执行——这正是"单指令多线程"（SIMT）的编程范式，和写普通 for 循环相比，唯一的心理负担是"要假装自己只是无数个并行执行的线程之一，不知道其他线程在做什么"。

### 2.2 Warp 带来的三个直接后果

Warp 这一层技术选择，直接决定了 Newton 具备的三个核心能力：

**GPU 原生并行**：Newton 的每一个物理量（刚体位姿、速度、关节角度、接触点信息）都以扁平的 Warp 数组形式存储（比如 `model.body_q` 是一个长度等于刚体总数的数组），仿真的每一步本质上是对这些数组做一批 GPU kernel 调用。这和"面向对象、每个物体是一个带方法的类实例"的传统仿真器设计完全不同——扁平数组结构天然适合 GPU 大规模并行，但也意味着 Newton 的编程习惯更接近"数据导向设计"（data-oriented design），第 2 章会详细展开这一点。

**自动微分**：因为 Warp kernel 本身支持自动求导（用 `wp.Tape()` 记录计算图、`tape.backward()` 反向传播），只要仿真的每一步都是用 Warp kernel 写的，整个"从初始状态到最终状态"的仿真过程理论上都可以求梯度——这正是第 8 章要讲的可微仿真的技术基础。

**跨平台编译**：同一份 Warp kernel 代码，可以编译到 CUDA GPU 上跑，也可以编译到纯 CPU 上跑（速度慢但能跑）。这意味着 Newton 的用户在没有 NVIDIA GPU 的机器上（比如 macOS，Newton 官方要求里明确写了"macOS 仅支持 CPU 模式"）也能跑通同样的代码，只是牺牲了并行加速。

### 2.3 Newton 和 warp.sim 的关系：继承与取代

细心的读者可能会发现，NVIDIA Warp 项目本身早就自带一个叫 `warp.sim` 的仿真子模块。Newton 官方文档明确说明：**Newton 继承并"泛化"了 `warp.sim`，而 `warp.sim` 模块本身已经被标记为废弃（deprecated）**。这不是简单的改名——`warp.sim` 是 Warp 团队为了展示 Warp 的能力而写的一个相对轻量的示例性仿真模块，而 Newton 是一个有 NVIDIA、Google DeepMind、Disney Research 三方专门投入、面向生产级机器人仿真需求、有独立治理结构（归属 Linux Foundation）的完整项目。可以把这个关系类比成："一个框架自带的 demo 应用，被重新设计、扩充成了一个独立的、专业的开源产品"。

## 三、Newton 的三方联合背景：为什么是这三家

Newton 项目由 **NVIDIA**、**Google DeepMind**、**Disney Research** 三方发起，这个组合本身透露了项目的定位：

- **NVIDIA** 带来了 Warp（GPU kernel 框架）、OpenUSD 生态（Omniverse/Isaac Sim 的场景描述标准）、以及硬件层面的 GPU 并行优化经验
- **Google DeepMind** 带来了 MuJoCo（业界公认最精确稳定的机器人物理引擎之一）以及 MuJoCo Warp（他们自己把 MuJoCo 移植到 GPU 上的项目）
- **Disney Research** 带来了在动画、软体仿真、布料/绳缆物理方向的长期技术积累（Newton 支持的 VBD 求解器、Style3D 布料求解器等，都和这条技术脉络相关）

这三方的技术资产合流，直接反映在 Newton 现在的求解器矩阵上：MuJoCo Warp 是 DeepMind 的贡献，VBD/Style3D 这类面向柔性体的求解器带有 Disney Research 的技术印记，而整个 GPU kernel 层和 USD 集成是 NVIDIA 的强项。项目目前由 **Linux Foundation** 托管管理，代码采用 Apache-2.0 许可证、文档采用 CC-BY-4.0 许可证——这意味着它不是某一家公司的私有项目，而是一个开放治理、社区共建的基础设施项目，这也是为什么它敢于同时把 MuJoCo Warp、以及其他厂商未来可能贡献的求解器都容纳进同一套架构里，而不是排他地只支持自家的技术栈。

## 四、Newton 的四个核心设计目标

结合官方文档的表述，Newton 的设计目标可以归纳成四条，这四条会在后续每一章里反复出现，是理解具体设计选择"为什么这样做"的参照系：

### 4.1 GPU 加速（GPU-accelerated）

不是"支持在 GPU 上跑"，而是"默认假设在 GPU 上跑，CPU 模式是退化选项"。这直接影响了数据结构设计——所有的模型数据都是扁平数组，所有的计算逻辑都写成可以大规模并行的 kernel 形式，即使某个操作本质上是"串行"的（比如某些图着色、图遍历类算法），也要想办法改写成能在 GPU 线程网格上跑的形式。

### 4.2 可微分（Differentiable）

物理仿真如果能对参数（初始速度、控制力、关节刚度等）求梯度，就能直接用于基于梯度的轨迹优化、系统辨识（system identification）、以及某些强化学习算法的训练加速。这个能力的代价是：不是所有求解器都能轻松做到可微——第 8 章会具体讲哪些求解器支持到什么程度的可微，以及可微仿真本身有哪些理论和工程上的限制（比如接触碰撞这种本质上不连续的过程，梯度的意义需要额外讨论）。

### 4.3 可扩展（Extensible）

用户应该能方便地插入自定义的求解器、自定义的属性（第 2 章会讲到的 Custom Attributes 机制）、自定义的传感器，而不需要修改引擎核心代码。这是一个开源基础设施项目必须具备的能力——否则每个团队要支持自己的特殊需求都要 fork 一份代码维护，生态很难统一。

### 4.4 丰富的导入/导出格式（Rich Import/Export）

机器人仿真领域历史上积累了大量用 **URDF**（ROS 生态标准格式）和 **MJCF**（MuJoCo 原生格式）描述的机器人模型资产，同时工业渲染和数字孪生领域近年快速转向 **USD**（Universal Scene Description，Pixar 发起、现由 Alliance for OpenUSD 维护的标准）。Newton 选择同时支持三种格式的导入，并且专门设计了"schema resolver"机制（第 2 章详述）来处理不同格式描述同一物理属性时的语义差异——这个设计直接反映了"不要求用户抛弃已有资产库重新建模"这个现实主义的工程考量。

## 五、和读者最切身相关的问题：Newton 值得学吗

### 5.1 判断标准

如果你的机器人学习/仿真工作满足以下任意一条，Newton 值得投入学习成本：

- 需要在同一个项目里既跑大规模并行 RL 训练，又需要精确的接触/铰接体动力学（不想在"MuJoCo 精确但慢"和"PhysX 快但接触建模粗糙"之间二选一）
- 场景资产同时包含 URDF/MJCF 遗留资产和新的 USD 数字孪生资产，不想维护两套转换脚本
- 需要柔性体（绳缆、布料、可变形物体）和刚体机器人在同一个仿真里耦合交互（比如机器人操作一根电缆）
- 关心可微仿真、基于梯度的轨迹优化或系统辨识
- 已经在用 NVIDIA Isaac Lab/Isaac Sim，想要一个原生对接的、比现有 PhysX 后端在接触精度上更强的物理选项

### 5.2 目前的成熟度提示

写这篇文章时（2026 年），Newton 的部分子系统（比如 Kamino 求解器、耦合求解器框架 CoupledADMM/CoupledProxy）明确标注为"实验性"（experimental），官方文档也多次提醒 API 可能变化。这不是缺点，而是一个真实的工程状态提示——如果你的项目对 API 稳定性要求很高（比如要长期维护的生产系统），建议优先使用文档里明确标注为稳定的部分（核心 ModelBuilder/Model/State API、MuJoCo 求解器、XPBD/VBD 等成熟求解器），对实验性功能保持关注但谨慎依赖。这个系列后续章节会在涉及实验性功能时明确标注。

## 六、本系列接下来要讲什么

这一章建立了"为什么"，接下来的章节会依次拆解"怎么做"：

- **第 2 章**会讲 Newton 的五件套核心数据模型——`ModelBuilder`（构建期）、`Model`（静态结构）、`State`（动态状态）、`Control`（控制输入）、`Contacts`（接触信息）——这是理解后面一切具体功能的地基。
- **第 3 章**讲铰接体（机械臂、人形机器人这类由关节连接的多刚体系统）怎么被表示和计算，广义坐标和最大坐标这两套并存的表示法各自的作用。
- **第 4 章**深入碰撞检测流水线，讲清楚"几万个形状怎么在 GPU 上高效找出真正碰撞的那几百对"这个工程问题。
- **第 5 章**系统对比六种求解器，给出一个可操作的选型指南。
- **第 6 章**专门讲 MuJoCo Warp 集成的细节——这是 Newton 目前最成熟、最常用的求解器后端，值得单独一章。
- **第 7 章**讲多环境并行（Worlds 机制）——强化学习训练的关键基础设施。
- **第 8 章**讲可微仿真的原理和限制。
- **第 9 章**讲 Actuator（执行器）和 Sensor（传感器）这两套外围系统，把整个"控制指令进来、观测数据出去"的闭环讲完整。

下一章从最基础的问题开始：Newton 的核心数据模型为什么要拆成这五个对象，而不是像很多传统引擎那样用一个大的"World"或"Scene"对象把所有东西装在一起。
